# PART 5: HELM TEMPLATING FUNDAMENTALS


## Goal

Learn the Go-template concepts Helm uses to transform reusable chart templates and configuration values into valid Kubernetes manifests.

In Part 4, you learned how to define default values, create environment-specific values files, apply command-line overrides, and validate configuration.

In Part 5, you will learn how Helm actually processes those values.

You will work with template expressions, built-in objects, context, pipelines, quoting, whitespace control, indentation, YAML generation, and rendering errors.

By the end, you will build a working Deployment and Service template, deliberately introduce several rendering failures, diagnose them, and correct them.

The central mental model is:

```
Helm Chart
    │
    ├── Chart.yaml
    ├── values.yaml
    └── templates/
          ├── deployment.yaml
          └── service.yaml
                │
                ▼
        Go Template Engine
                │
                ├── Built-in Objects
                ├── Template Expressions
                ├── Functions
                ├── Pipelines
                └── Whitespace Control
                │
                ▼
        Rendered Kubernetes YAML
                │
                ▼
        Kubernetes API
                │
                ▼
        Kubernetes Resources
```

The fundamental distinction is:

Helm templates are instructions for generating Kubernetes YAML. Kubernetes receives the rendered YAML, not the template expressions.

# 2. Why Helm needs a template engine

Consider a Kubernetes Deployment:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
```

The Deployment contains fixed values.

If another environment requires five replicas, someone must change the manifest or maintain a separate copy.

Helm allows the Deployment to become a template:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
```

The values file provides:

```
replicaCount: 3
```

The release name comes from the Helm command:

```
helm template payments-api ./my-chart
```

Helm renders:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
```

The result is ordinary Kubernetes YAML.

No Helm expressions remain.

## 2.1 What the template engine does

The template engine evaluates expressions and produces text.

It does not directly create Deployments, Services, Pods, or ConfigMaps.

Helm's installation and upgrade workflow subsequently sends the rendered Kubernetes resources to the Kubernetes API.

This separation is important.

```
Template Evaluation
        ≠
Kubernetes Resource Creation
```

You can render a chart without installing it.

That makes templating useful for development, testing, code review, and CI/CD validation.

# 3. Template expressions: `{{ }}`

The most recognizable Helm template syntax is:

```
{{ }}
```

A template expression evaluates an instruction and may insert its result into the output.

For example:

```
{{ .Values.replicaCount }}
```

If:

```
replicaCount: 3
```

the expression produces:

```
3
```

## 3.1 Basic examples

| Template expression              | Example result |
| -------------------------------- | -------------- |
| `{{ .Release.Name }}`            | `web-dev`      |
| `{{ .Release.Namespace }}`       | `helm-lab`     |
| `{{ .Chart.Name }}`              | `web-app`      |
| `{{ .Chart.Version }}`           | `0.1.0`        |
| `{{ .Values.replicaCount }}`     | `3`            |
| `{{ .Values.image.repository }}` | `nginx`        |

The exact results depend on the chart, values, and rendering command.

## 3.2 Expressions inside YAML

A template can contain both static YAML and dynamic expressions:

```
metadata:
  name: {{ .Release.Name }}-web
  labels:
    app.kubernetes.io/name: {{ .Chart.Name }}
```

With release name `demo` and chart name `web-app`, Helm renders:

```
metadata:
  name: demo-web
  labels:
    app.kubernetes.io/name: web-app
```

Only the expressions are evaluated.

The surrounding YAML remains ordinary text.

## 3.3 Template actions are not limited to printing values

Expressions can also control rendering.

For example:

```
{{- if .Values.service.enabled }}
apiVersion: v1
kind: Service
# ...
{{- end }}
```

This conditionally renders a Service.

Other actions, including `range`, `with`, `define`, and `include`, become important in subsequent chapters.

Part 5 focuses on the foundations needed to understand them.

# 4. Helm's built-in objects

Helm provides several built-in objects to templates.

These objects contain information about the chart, release, Kubernetes capabilities, files, and configuration.

| Object          | Purpose                                          |
| --------------- | ------------------------------------------------ |
| `.Values`       | Chart configuration values                       |
| `.Release`      | Information about the current Helm release       |
| `.Chart`        | Metadata from `Chart.yaml`                       |
| `.Capabilities` | Kubernetes API and Helm capabilities             |
| `.Template`     | Information about the current template           |
| `.Files`        | Access to eligible files packaged with the chart |

These objects are available from the root template context. Access may change when the current dot changes inside a scoped template block.

# 5. The `.Values` object

`.Values` contains the effective chart configuration.

Example `values.yaml`:

```
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  port: 80
```

Template:

```
spec:
  replicas: {{ .Values.replicaCount }}
```

Nested access:

```
{{ .Values.image.repository }}
```

```
{{ .Values.image.tag }}
```

```
{{ .Values.service.port }}
```

## 5.1 Accessing nested values

The expression:

```
{{ .Values.image.repository }}
```

means:

```
Current context
      │
      ▼
    Values
      │
      ▼
     image
      │
      ▼
  repository
```

If `image.repository` is `nginx`, the expression evaluates to `nginx`.

## 5.2 Missing values

Consider:

```
{{ .Values.image.digest }}
```

If `digest` is not defined, the result depends on the expression and context. Some missing lookups may render an empty-like value, while missing parent maps or downstream function operations may cause errors.

Do not assume every missing value produces a harmless empty string.

For required settings, use explicit validation.

For example:

```
{{ required "image.repository must be configured" .Values.image.repository }}
```

A chart can also use `values.schema.json` to validate configuration before rendering.

# 6. The `.Release` object

`.Release` provides information about the current release.

Important properties include:

```
{{ .Release.Name }}
{{ .Release.Namespace }}
{{ .Release.IsInstall }}
{{ .Release.IsUpgrade }}
{{ .Release.Revision }}
{{ .Release.Service }}
```

## 6.1 Release name

Command:

```
helm template payments ./my-chart
```

Template:

```
metadata:
  name: {{ .Release.Name }}
```

Rendered:

```
metadata:
  name: payments
```

The release name is an important naming input.

A single chart can be installed multiple times with different release names.

For example:

```
Chart: web-app

Release A: frontend-dev
Release B: frontend-staging
Release C: frontend-production
```

Each release can produce separately named resources, provided the chart's naming strategy supports this.

## 6.2 Release namespace

Template:

```
metadata:
  namespace: {{ .Release.Namespace }}
```

Render:

```
helm template demo ./my-chart \
  --namespace helm-lab
```

The expression produces:

```
metadata:
  namespace: helm-lab
```

A namespace does not necessarily need to be written into every namespaced resource template; Helm can use the release namespace when applying resources.

For this lab, you will keep namespace selection in the Helm command.

## 6.3 Install and upgrade flags

Helm provides:

```
{{ .Release.IsInstall }}
```

and:

```
{{ .Release.IsUpgrade }}
```

These booleans can support install-specific or upgrade-specific template behavior.

However, avoid making application templates unnecessarily dependent on whether an operation is an installation or upgrade.

A declarative chart should usually describe the desired application state.

## 6.4 Release revision

```
{{ .Release.Revision }}
```

A release revision identifies a particular release operation in Helm's history.

Do not confuse it with a Git commit, chart version, or application version.

Also note that `helm template` simulates a rendering context; it does not retrieve the live revision history of an installed release.

# 7. The `.Chart` object

`.Chart` exposes metadata from `Chart.yaml`.

Example:

```
apiVersion: v2
name: web-app
description: A Helm learning application
type: application
version: 0.1.0
appVersion: "1.27"
```

Templates can access:

```
{{ .Chart.Name }}
```

```
{{ .Chart.Version }}
```

```
{{ .Chart.AppVersion }}
```

```
{{ .Chart.Description }}
```

## 7.1 Chart version versus application version

These represent different things.

```
Chart Version
    │
    └── Version of the Helm packaging/configuration

Application Version
    │
    └── Version of the application represented by the chart
```

For example:

```
version: 0.3.0
appVersion: "1.27"
```

The chart version is `0.3.0`.

The application version is `1.27`.

They do not need to match.

## 7.2 Using chart metadata in labels

Template:

```
metadata:
  labels:
    helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | quote }}
```

For chart `web-app` version `0.1.0`, the rendered value is:

```
metadata:
  labels:
    helm.sh/chart: "web-app-0.1.0"
```

The `replace` function helps make SemVer build metadata compatible with Kubernetes label-value restrictions.

This pattern is common in production charts.

# 8. The `.Capabilities` object

`.Capabilities` describes capabilities available to Helm during rendering.

Important properties include:

```
{{ .Capabilities.KubeVersion.Version }}
```

```
{{ .Capabilities.KubeVersion.Major }}
```

```
{{ .Capabilities.KubeVersion.Minor }}
```

```
{{ .Capabilities.APIVersions }}
```

```
{{ .Capabilities.HelmVersion.Version }}
```

## 8.1 Why capabilities matter

Kubernetes APIs evolve.

An API supported by one cluster version may be unavailable in another.

A chart may need to determine which API version to use.

For example:

```
{{- if .Capabilities.APIVersions.Has "networking.k8s.io/v1/Ingress" }}
# Render a supported networking.k8s.io/v1 Ingress
{{- end }}
```

This checks whether the specified API version is advertised in the rendering capabilities.

It does not prove that every desired field or controller behavior is supported.

## 8.2 Offline rendering

When using `helm template`, Helm may rely on default or explicitly supplied Kubernetes capability information rather than querying a live cluster.

For example:

```
helm template demo ./my-chart \
  --kube-version 1.30.0
```

The specified version affects capability-aware rendering.

Use a version appropriate for the cluster you are targeting.

## 8.3 Production implication

A chart that renders successfully for one Kubernetes version may not be compatible with another.

Capabilities help manage API compatibility, but rendered manifests still need validation against the target cluster.

# 9. The `.Template` object

`.Template` contains information about the current template.

Important properties include:

```
{{ .Template.Name }}
```

```
{{ .Template.BasePath }}
```

For example, `.Template.Name` may identify a path such as:

```
web-app/templates/deployment.yaml
```

The exact path depends on the chart.

## 9.1 Why this is useful

Template metadata can help with debugging and certain reusable template patterns.

However, it is not usually necessary to insert template file paths into Kubernetes resources.

A template's source path is an implementation detail.

## 9.2 A useful diagnostic example

You can temporarily add a template comment:

```
{{/* Current template: */}}
{{/* Inspect .Template.Name while debugging */}}
```

Or output a YAML comment:

```
# Rendered from: {{ .Template.Name }}
```

The latter appears in the generated YAML as a comment.

Use this for diagnostics rather than as a permanent production requirement.

# 10. The `.Files` object

`.Files` allows templates to read eligible files included in the chart.

For example, consider:

```
my-chart/
├── Chart.yaml
├── values.yaml
├── files/
│   └── application.properties
└── templates/
    └── configmap.yaml
```

The file:

```
files/application.properties
```

contains:

```
LOG_LEVEL=info
CACHE_ENABLED=true
```

A template can use:

```
{{ .Files.Get "files/application.properties" }}
```

## 10.1 Creating a ConfigMap from a file

Example:

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  application.properties: |
{{ .Files.Get "files/application.properties" | indent 4 }}
```

Rendered:

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-config
data:
  application.properties: |
    LOG_LEVEL=info
    CACHE_ENABLED=true
```

This is useful for packaging application configuration files.

## 10.2 Important restrictions

`.Files` does not provide unrestricted access to your local filesystem.

It cannot read arbitrary files outside the chart.

It also cannot normally access files under `templates/`, files excluded by `.helmignore`, or files that are otherwise inaccessible to the current chart.

Subcharts have their own file boundaries.

## 10.3 Security consideration

Files included in charts may become part of packaged chart artifacts.

Do not package plaintext credentials, private keys, or production secrets in ordinary chart files.

# 11. Understanding the dot (`.`)

The dot is one of the most important Go-template concepts.

```
.
```

It represents the current context.

At the top level of a Helm template, the dot normally refers to the root rendering context.

From that context, you can access:

```
.Values
.Release
.Chart
.Capabilities
.Template
.Files
```

## 11.1 Why context matters

Consider:

```
{{ .Values.image.repository }}
```

This works when the current dot is the root context.

But inside a `with` block:

```
{{- with .Values.image }}
repository: {{ .repository }}
tag: {{ .tag }}
{{- end }}
```

the dot inside the block refers to the `image` map.

Therefore:

```
{{ .repository }}
```

is valid inside that scope.

But:

```
{{ .Values.image.repository }}
```

would no longer refer to the root values object through the current dot.

## 11.2 Accessing the root context

Helm templates support the root-context variable:

```
$
```

For example:

```
{{- with .Values.image }}
repository: {{ .repository }}
release: {{ $.Release.Name }}
{{- end }}
```

The `$` reference preserves access to the root context in this example.

This becomes especially important in reusable templates and loops.

## 11.3 Mental model

```
Root Context
     │
     ├── .Values
     ├── .Release
     ├── .Chart
     └── .Capabilities
             │
             ▼
       Enter with block
             │
             ▼
       Dot changes
             │
             ├── .repository
             └── .tag

       $ still refers to root
```

A large percentage of Helm templating mistakes are caused by misunderstanding context.

# 12. Pipelines

Pipelines allow the output of one expression to be passed into another function.

The pipe symbol is:

```
|
```

Example:

```
{{ .Values.environment | upper }}
```

If:

```
environment: development
```

the result is:

```
DEVELOPMENT
```

## 12.1 Pipeline mental model

```
Input Value
    │
    ▼
Function 1
    │
    ▼
Function 2
    │
    ▼
Rendered Output
```

Example:

```
{{ .Values.environment | upper | quote }}
```

The steps are:

```
development
     │
     ▼
   upper
     │
     ▼
DEVELOPMENT
     │
     ▼
   quote
     │
     ▼
"DEVELOPMENT"
```

## 12.2 Function arguments in pipelines

Consider:

```
{{ .Values.environment | default "development" }}
```

The piped value is passed as the final argument to `default`.

Conceptually, this is equivalent to:

```
{{ default "development" .Values.environment }}
```

This matters when working with functions that accept multiple arguments.

## 12.3 Useful pipeline functions

| Function  | Purpose                          | Example                     |
| --------- | -------------------------------- | --------------------------- |
| `quote`   | Quote a value as a string        | `value \\| quote`           |
| `upper`   | Convert to uppercase             | `value \\| upper`           |
| `lower`   | Convert to lowercase             | `value \\| lower`           |
| `default` | Supply fallback for empty values | `value \\| default "x"`     |
| `trim`    | Remove surrounding whitespace    | `value \\| trim`            |
| `replace` | Replace text                     | `value \\| replace "." "-"` |
| `toYaml`  | Convert a value to YAML          | `value \\| toYaml`          |
| `indent`  | Indent text                      | `value \\| indent 4`        |
| `nindent` | Add newline and indent           | `value \\| nindent 4`       |

These functions are widely used in Helm charts.

# 13. Using `default`

Consider:

```
image:
  repository: nginx
  tag: ""
```

Template:

```
{{ .Values.image.tag | default .Chart.AppVersion }}
```

If `appVersion` is `"1.27"`, the fallback result is:

```
1.27
```

This is useful for optional settings.

However, `default` considers several values empty, including:

```
false
0
""
null
empty lists
empty maps
```

Therefore, this pattern can be problematic:

```
{{ .Values.featureEnabled | default true }}
```

An explicitly configured `false` may be replaced by `true`.

For booleans where `false` is meaningful, use a presence-aware approach or a clear default defined in `values.yaml`.

Do not use `default` as a substitute for understanding types and missing-value behavior.

# 14. Quoting in templates

Kubernetes expects particular data types.

Some fields require integers:

```
replicas: 3
```

Some require strings:

```
metadata:
  labels:
    environment: "production"
```

Some require booleans:

```
securityContext:
  readOnlyRootFilesystem: true
```

Helm templates must preserve these distinctions.

## 14.1 Correct numeric rendering

```
replicas: {{ .Values.replicaCount }}
```

If `replicaCount` is `3`, the output is:

```
replicas: 3
```

## 14.2 Correct string rendering

```
metadata:
  labels:
    environment: {{ .Values.environment | quote }}
```

Rendered:

```
metadata:
  labels:
    environment: "production"
```

## 14.3 Environment variables

Kubernetes environment-variable values are strings.

Template:

```
env:
  - name: FEATURE_ENABLED
    value: {{ .Values.featureEnabled | quote }}
```

If the value is boolean `false`, the output becomes:

```
env:
  - name: FEATURE_ENABLED
    value: "false"
```

This is correct because `EnvVar.value` is a string.

## 14.4 Avoid quoting everything

Incorrect:

```
replicas: {{ .Values.replicaCount | quote }}
```

This may produce:

```
replicas: "3"
```

which does not match the Kubernetes integer field type.

Quoting should follow the target Kubernetes field's type, not a universal formatting rule.

# 15. YAML and Go templates are separate languages

Helm chart templates combine two syntaxes:

```
YAML
+
Go Template Actions
```

Consider:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
```

The YAML structure is:

```
apiVersion
kind
metadata
name
```

The Go-template expression is:

```
{{ .Release.Name }}
```

Helm evaluates the expression and produces text.

Then the rendered text must be interpretable as Kubernetes YAML.

This means a template can be syntactically valid as a Go template but still produce invalid YAML.

## Example

Template:

```
metadata:
  labels:
    app: {{ .Values.applicationName }}
```

Suppose:

```
applicationName: "demo: test"
```

Without appropriate quoting, the rendered output may be:

```
metadata:
  labels:
    app: demo: test
```

That is invalid YAML in this position because the unquoted value contains a colon followed by a space.

Safer:

```
metadata:
  labels:
    app: {{ .Values.applicationName | quote }}
```

Rendered:

```
metadata:
  labels:
    app: "demo: test"
```

This fixes the YAML quoting issue.

However, `"demo: test"` is not a valid Kubernetes label value. The application must still use a label-compatible value.

This demonstrates two different validation layers:

```
Template Syntax
      ↓
YAML Syntax
      ↓
Kubernetes API Schema
      ↓
Kubernetes Semantic Rules
```

Passing one layer does not guarantee passing the next.

# 16. Whitespace in Helm templates

Whitespace is significant in YAML.

Consider:

```
metadata:
  labels:
    app: nginx
```

The indentation expresses nesting.

If Helm produces:

```
metadata:
labels:
app: nginx
```

the structure changes and no longer represents the intended Kubernetes metadata.

Helm templates must produce correctly indented YAML.

Whitespace includes:

- Spaces.
- Tabs.
- Newline characters.
- Blank lines.

Kubernetes YAML should generally use spaces for indentation.

# 17. Whitespace trimming

Go templates provide whitespace trimming syntax.

```
{{-
```

trims whitespace immediately before the action.

```
-}}
```

trims whitespace immediately after the action.

Both forms can be used:

```
{{- .Values.applicationName -}}
```

The hyphen must be separated from the expression by whitespace to act as a trim marker.

## 17.1 Example without trimming

Template:

```
name:
  {{ .Values.applicationName }}
```

This may produce:

```
name:
  nginx
```

Depending on the YAML field, that layout may be inappropriate.

A more direct expression is:

```
name: {{ .Values.applicationName }}
```

## 17.2 Trimming control statements

Consider:

```
{{- if .Values.service.enabled }}
apiVersion: v1
kind: Service
{{- end }}
```

The leading hyphens remove whitespace before the control actions.

This helps prevent unwanted blank lines.

## 17.3 Dangerous trimming

Consider:

```
food: "PIZZA"
{{- if .Values.favoriteDrink }}
mug: "true"
{{- end }}
```

This is generally manageable because the newline following the `if` action remains.

But adding a trailing trim marker carelessly can remove a required newline.

For example:

```
food: "PIZZA"
{{- if .Values.favoriteDrink -}}
mug: "true"
{{- end }}
```

The whitespace around the action may be removed so aggressively that the output becomes:

```
food: "PIZZA"mug: "true"
```

This is invalid YAML.

Whitespace trimming is useful, but it must be applied deliberately.

# 18. Understanding `indent`

The `indent` function adds spaces to the beginning of each line in a string.

Example:

```
{{ "first\nsecond" | indent 4 }}
```

Result:

```
    first
    second
```

`indent` does not automatically insert a newline before the text.

This matters when embedding YAML structures.

## Example

Suppose `.Values.resources` contains:

```
requests:
  cpu: 100m
  memory: 128Mi
```

Template:

```
resources:
{{ toYaml .Values.resources | indent 2 }}
```

Rendered:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

This works because the template already includes a newline after `resources:`.

# 19. Understanding `nindent`

`nindent` means newline plus indentation.

Example:

```
{{ "first\nsecond" | nindent 4 }}
```

Result:

```

    first
    second
```

The output begins with a newline.

This makes `nindent` particularly useful in Helm templates.

## Example

Template:

```
resources: {{ toYaml .Values.resources | nindent 2 }}
```

Rendered:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
```

The inserted newline moves the structured YAML below `resources:`.

## `indent` versus `nindent`

| Function  | Adds spaces | Adds initial newline |
| --------- | ----------- | -------------------- |
| `indent`  | Yes         | No                   |
| `nindent` | Yes         | Yes                  |

Neither function automatically determines the correct indentation depth.

You must calculate that depth based on the surrounding YAML structure.

# 20. Understanding `toYaml`

`toYaml` serializes a value into YAML text.

This is especially useful for maps and lists.

Example values:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

Instead of referencing every nested field individually:

```
resources:
  requests:
    cpu: {{ .Values.resources.requests.cpu }}
    memory: {{ .Values.resources.requests.memory }}
  limits:
    memory: {{ .Values.resources.limits.memory }}
```

you can write:

```
resources:
  {{- toYaml .Values.resources | nindent 2 }}
```

This preserves the supplied structure.

## 20.1 Why `toYaml` is useful

It reduces repetition.

It allows chart users to supply structured configuration.

It makes it easier to pass Kubernetes-native maps and lists into templates.

## 20.2 Why `toYaml` still requires care

`toYaml` does not guarantee that the resulting structure is valid for the Kubernetes field where it is inserted.

For example, a user could supply:

```
resources:
  unknownField: something
```

Helm may successfully convert this map to YAML.

But Kubernetes may reject the resulting container resources configuration.

Therefore:

```
Successful toYaml
        ≠
Valid Kubernetes Resource
```

# 22. Template comments

Go templates support comments using:

```
{{/* comment */}}
```

Example:

```
{{/* Render the application Deployment */}}
apiVersion: apps/v1
kind: Deployment
```

Template comments are removed during rendering.

They do not appear in the resulting Kubernetes YAML.

## 22.1 YAML comments versus template comments

YAML comment:

```
# This is a YAML comment
```

Template comment:

```
{{/* This is a Go-template comment */}}
```

The difference:

| Comment type                    | Appears in rendered YAML? |
| ------------------------------- | ------------------------- |
| YAML `#` comment                | Usually yes               |
| Go-template `{{/* */}}` comment | No                        |

## 22.2 Important interaction

A YAML comment does not disable Go-template evaluation.

For example:

```
# {{ .Values.applicationName }}
```

Helm still evaluates the expression.

The rendered YAML comment may become:

```
# nginx
```

If you need to prevent template evaluation, use a Go-template comment or remove the template expression.

# 23. Common rendering errors

Helm rendering errors can be grouped into several categories.

| Error category            | Example                               |
| ------------------------- | ------------------------------------- |
| Template syntax           | Missing `}}`                          |
| Context                   | Accessing `.Values` after dot changes |
| Missing value             | Referencing an absent nested object   |
| Type mismatch             | String where integer is expected      |
| YAML indentation          | Incorrect nesting                     |
| Whitespace trimming       | Required newline removed              |
| Invalid Kubernetes schema | Unsupported field                     |
| Semantic configuration    | Service selector does not match Pods  |

These errors occur at different stages.

## 23.1 Template parsing error

Example:

```
{{ .Values.replicaCount
```

The expression is incomplete.

Helm cannot parse the template.

## 23.2 YAML rendering error

Example:

```
metadata:
  labels:
    app: nginx
  environment: production
    team: platform
```

The indentation is inconsistent.

The YAML parser may reject the document.

## 23.3 Kubernetes schema error

Example:

```
spec:
  replicas: "three"
```

The YAML may parse, but Kubernetes expects an integer.

## 23.4 Application behavior error

A manifest can be valid and successfully installed while still failing to run the application correctly.

For example, a Service may target a port on which the application is not listening.

Helm template validation alone cannot detect every runtime problem.

# 49. Production templating principles

Helm templates should be predictable.

A production-quality chart should favor:

Clarity: Templates should be understandable by someone who did not write them.

Consistency: Similar resources should follow similar naming, labeling, and configuration patterns.

Minimal complexity: Avoid unnecessary template logic.

Validation: Invalid values should fail early.

Stable naming: Resource names and selectors should not change unexpectedly.

Correct types: Render Kubernetes fields using the types the API expects.

Explicit scope: Avoid relying on ambiguous dot behavior.

Safe defaults: Avoid exposing services or enabling risky features unintentionally.

Reviewability: Rendered YAML should be inspectable before deployment.

Compatibility: Charts should account for supported Kubernetes API versions.

# 50. Common anti-patterns

## Anti-pattern 1: Treating templates like arbitrary programming code

Helm supports logic, but excessive logic makes charts difficult to maintain.

A chart should primarily describe Kubernetes resources.

Complex business logic belongs in the application or appropriate deployment tooling.

## Anti-pattern 2: Quoting every value

This causes type mismatches.

Use quoting based on the expected Kubernetes field type.

## Anti-pattern 3: Hardcoding every setting

This reduces chart reusability.

Expose values that reasonably vary between environments.

## Anti-pattern 4: Exposing every Kubernetes field

This makes the values interface difficult to maintain.

Choose a deliberate configuration API.

## Anti-pattern 5: Ignoring scope changes

Code that works at root scope may fail inside `with` or `range`.

Use `$` or explicit variables where appropriate.

## Anti-pattern 6: Using aggressive whitespace trimming

Excessive `{{-` and `-}}` can concatenate YAML fields.

Always inspect rendered output.

## Anti-pattern 7: Assuming successful rendering means successful deployment

Rendering validates only part of the deployment lifecycle.

A valid manifest can still fail scheduling, image pulling, readiness checks, or application startup.

# 51. Helm templating debugging workflow

Use the following sequence when troubleshooting a chart.

1

Verify chart structure

2

Inspect effective values

3

Run helm lint

4

Render with helm template --debug

5

Locate the failing template

6

Inspect rendered YAML and indentation

7

Check quoting and Kubernetes field types

8

Check dot context and pipelines

9

Validate against Kubernetes API

10

Install in a disposable cluster and verify behavior

Useful commands:

```
helm lint ./templating-web
```

```

```

```
helm show values ./templating-web
```

```
helm template demo ./templating-web \
  --show-only templates/deployment.yaml
```

```

  --output-dir rendered
```

The `--show-only` option is useful for focusing on one template. It does not guarantee unrelated template errors will never affect the rendering operation.

# 52. Production CI/CD templating validation

A production pipeline should not rely only on successful Helm command execution.

A more complete workflow is:

```
Source Code
    │
    ▼
Chart Validation
    │
    ▼
Values Validation
    │
    ▼
Helm Template Rendering
    │
    ▼
YAML Parsing
    │
    ▼
Kubernetes Schema Validation
    │
    ▼
Security and Policy Validation
    │
    ▼
Rendered Manifest Review
    │
    ▼
Deployment Approval
    │
    ▼
Cluster Deployment
    │
    ▼
Post-Deployment Verification
```

For example:

```
helm lint ./charts/payments \
  -f environments/production/payments.yaml
```

Then:

```
helm template payments ./charts/payments \
  -f environments/production/payments.yaml \
  > rendered/payments-production.yaml
```

The rendered manifest can be passed to appropriate schema-validation and policy-checking tools.

For a live cluster:

```
kubectl apply \
  --dry-run=server \
  -f rendered/payments-production.yaml
```

Use explicit Kubernetes context and namespace selection in real deployment pipelines.
