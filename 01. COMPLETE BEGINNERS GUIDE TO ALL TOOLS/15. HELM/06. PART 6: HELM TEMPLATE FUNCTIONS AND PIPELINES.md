# PART 6: HELM TEMPLATE FUNCTIONS AND PIPELINES

Level: Beginner to Intermediate → Production Foundations Prerequisite: Parts 1–5 Lab environment: Disposable Kubernetes cluster, Helm CLI, kubectl Primary focus: Data transformation, defensive templating, reusable configuration, and predictable rendering

## Goal

Learn how to use Helm template functions and pipelines to transform chart configuration safely, validate required values, generate structured Kubernetes manifests, and prevent common configuration mistakes.

In Part 5, you learned how Helm evaluates Go-template expressions, accesses built-in objects, handles context, and renders YAML.

Part 6 takes that foundation further.

You will learn not only how functions work, but when to use them, when not to use them, and how to recognize function-related failures before deploying to Kubernetes.

By the end, you will be able to build a chart that:

- Provides sensible defaults without overriding intentional values.
- Rejects missing mandatory configuration.
- Converts and formats strings safely.
- Builds Kubernetes labels and annotations.
- Generates ConfigMaps from structured values.
- Handles lists and dictionaries.
- Uses pipelines for readable transformations.
- Avoids nondeterministic output and unnecessary cluster queries.
- Detects and repairs function and pipeline errors.

# 1. The Helm function mental model

A Helm template function accepts input, performs an operation, and returns a result.

For example:

```
{{ .Values.environment | upper }}
```

If the configured environment is `development`, Helm produces `DEVELOPMENT`.

INPUT VALUE

## development

TEMPLATE FUNCTION

## upper

RENDERED OUTPUT

## DEVELOPMENT

Helm functions operate during chart rendering. Kubernetes does not evaluate Helm functions.

The execution flow is:

```
values.yaml
    │
    ▼
.Values
    │
    ▼
Helm Template Expression
    │
    ▼
Function / Pipeline
    │
    ▼
Rendered YAML
    │
    ▼
Kubernetes API
    │
    ▼
Kubernetes Resources
```

The goal is not to add functions everywhere. It is to use them where they make configuration safer, clearer, and more maintainable.

# 3. Where Helm functions come from

Helm uses Go's `text/template` engine and provides additional functions for chart authors.

Its function collection includes functions from the Sprig library, along with Helm-specific functions.

Conceptually:

```
Go Template Engine
        +
Sprig Functions
        +
Helm-Specific Functions
        │
        ▼
Helm Chart Templating
```

These function groups provide capabilities such as string manipulation, conversion, collections, serialization, encoding, cryptography, and Kubernetes-aware operations.

Not every Sprig function is exposed by Helm, and Helm also supplies its own functions such as `include`, `required`, `lookup`, and YAML conversion helpers.

The installed Helm version determines the exact available function set.

## 3.1 Function categories

| Category                    | Examples                                                 | Typical purpose                      |
| --------------------------- | -------------------------------------------------------- | ------------------------------------ |
| Defaults and validation     | `default`, `required`, `empty`, `coalesce`               | Manage optional and mandatory values |
| Strings                     | `quote`, `upper`, `lower`, `trim`, `replace`, `contains` | Format configuration                 |
| Formatting                  | `printf`, `print`, `println`                             | Build output strings                 |
| Serialization               | `toYaml`, `fromYaml`, `toJson`, `fromJson`               | Work with structured data            |
| Indentation                 | `indent`, `nindent`                                      | Produce valid YAML nesting           |
| Types                       | `int`, `int64`, `float64`, `toString`, `kindOf`          | Convert or inspect types             |
| Lists                       | `list`, `append`, `concat`, `first`, `rest`              | Manage ordered collections           |
| Dictionaries                | `dict`, `get`, `hasKey`, `set`, `merge`, `deepCopy`      | Manage maps                          |
| Kubernetes                  | `lookup`                                                 | Query existing cluster resources     |
| Cryptography and randomness | `sha256sum`, `randAlphaNum`, certificate helpers         | Hash or generate data                |

# 4. Function invocation syntax

Helm supports direct function invocation.

```
{{ upper "development" }}
```

Output:

```
DEVELOPMENT
```

A function may accept multiple arguments.

For example:

```
{{ replace "-" "_" "web-api" }}
```

Output:

```
web_api
```

The order of arguments matters.

For `replace`, the order is:

```
Old String
    +
New String
    +
Input String
        ↓
     replace
        ↓
      Output
```

## 4.1 Direct calls versus pipelines

Direct:

```
{{ upper .Values.environment }}
```

Pipeline:

```
{{ .Values.environment | upper }}
```

Both produce the same result.

For transformations involving multiple steps, pipelines are often easier to read.

# 5. Pipelines in depth

The pipe operator is:

```
|
```

It sends the result of the expression on its left into the next function as the last argument.

Example:

```
{{ .Values.environment | default "development" | upper | quote }}
```

If `environment` is unset or empty:

```
Missing or empty value
         │
         ▼
default "development"
         │
         ▼
development
         │
         ▼
upper
         │
         ▼
DEVELOPMENT
         │
         ▼
quote
         │
         ▼
"DEVELOPMENT"
```

Rendered YAML:

```
data:
  ENVIRONMENT: "DEVELOPMENT"
```

## 5.1 Pipeline evaluation order

The functions execute from left to right.

```
{{ .Values.applicationName | trim | lower | replace " " "-" | quote }}
```

Given:

```
applicationName: "  Payments API  "
```

the transformation is:

```
"  Payments API  "
        │
        ▼
       trim
        │
        ▼
"Payments API"
        │
        ▼
       lower
        │
        ▼
"payments api"
        │
        ▼
 replace " " "-"
        │
        ▼
"payments-api"
        │
        ▼
       quote
        │
        ▼
"payments-api"
```

## 5.2 Why order matters

Compare:

```
{{ .Values.applicationName | trim | lower | quote }}
```

with:

```
{{ .Values.applicationName | quote | trim | lower }}
```

The second expression transforms a quoted representation of the value.

That can produce unexpected results.

General practice: Perform normalization and transformations first; apply output formatting such as `quote` at the end.

# 6. The `default` function

`default` provides a fallback when a value is considered empty.

Syntax:

```
{{ default FALLBACK VALUE }}
```

Pipeline form:

```
{{ VALUE | default FALLBACK }}
```

Example:

```
environment: ""
```

Template:

```
{{ .Values.environment | default "development" }}
```

Result:

```
development
```

## 6.1 Defaulting an image tag

`Chart.yaml`:

```
apiVersion: v2
name: function-lab
version: 0.1.0
appVersion: "1.27"
```

`values.yaml`:

```
image:
  repository: nginx
  tag: ""
```

Template:

```
{{ .Values.image.tag | default .Chart.AppVersion }}
```

Result:

```
1.27
```

This is a common chart design pattern.

## 6.2 What counts as empty?

The following values are generally considered empty by `default`:

| Value            | Considered empty? |
| ---------------- | ----------------- |
| `""`             | Yes               |
| `0`              | Yes               |
| `false`          | Yes               |
| `null`           | Yes               |
| Empty list       | Yes               |
| Empty map        | Yes               |
| Nonempty string  | No                |
| Positive integer | No                |
| `true`           | No                |

## 6.3 Dangerous boolean default

Consider:

```
featureEnabled: false
```

Template:

```
{{ .Values.featureEnabled | default true }}
```

This may render:

```
true
```

even though the user explicitly configured `false`.

The problem is that `false` is treated as empty.

A safer approach is to define the default in `values.yaml` and reference it directly:

```
featureEnabled: false
```

```
{{ .Values.featureEnabled }}
```

If a fallback must distinguish an absent key from a present `false`, use a presence check such as `hasKey`.

For example:

```
{{- if hasKey .Values "featureEnabled" }}
{{ .Values.featureEnabled }}
{{- else }}
false
{{- end }}
```

This preserves an explicitly configured `false`.

# 7. The `required` function

`required` rejects empty mandatory values.

Syntax:

```
{{ required "error message" VALUE }}
```

Example:

```
{{ required "image.repository must be configured" .Values.image.repository }}
```

If the repository is empty, Helm fails rendering with the supplied message.

## 7.1 Required application identifier

Values:

```
application:
  id: ""
```

Template:

```
metadata:
  name: {{ required "application.id is required" .Values.application.id | quote }}
```

The learner should observe that Helm stops rather than generating an invalid resource name.

For a real Kubernetes resource name, additional format validation is needed; `required` only checks emptiness.

## 7.2 Required is not complete validation

This expression:

```
{{ required "replicaCount required" .Values.replicaCount }}
```

rejects zero because `0` is considered empty.

But a zero-replica Deployment can be a valid and intentional configuration.

Use `required` for genuinely mandatory nonempty settings, not as a universal validation mechanism.

For type, range, and structural validation, prefer a `values.schema.json` file where appropriate.

## 7.3 Explicit failure with `fail`

Helm also provides `fail`.

Example:

```
{{- if lt (int .Values.replicaCount) 0 }}
{{- fail "replicaCount must not be negative" }}
{{- end }}
```

This demonstrates custom validation logic.

However, note that converting malformed input using `int` may produce a zero-like value rather than reporting every conversion failure. A JSON schema is generally better for enforcing an integer type.

# 8. The `quote` function

`quote` formats a value as a quoted string.

Example:

```
{{ .Values.environment | quote }}
```

Input:

```
environment: production
```

Output:

```
"production"
```

This is especially useful for Kubernetes fields requiring strings.

## 8.1 ConfigMap values

Kubernetes ConfigMap `data` values must be strings.

Template:

```
data:
  LOG_LEVEL: {{ .Values.config.logLevel | quote }}
  FEATURE_ENABLED: {{ .Values.config.featureEnabled | quote }}
```

Values:

```
config:
  logLevel: info
  featureEnabled: false
```

Rendered:

```
data:
  LOG_LEVEL: "info"
  FEATURE_ENABLED: "false"
```

## 8.2 Numeric fields must remain numeric

Correct:

```
spec:
  replicas: {{ .Values.replicaCount }}
```

Potentially incorrect:

```
spec:
  replicas: {{ .Values.replicaCount | quote }}
```

The second form produces a string, which does not match the Kubernetes Deployment schema.

## 8.3 Quoting does not validate Kubernetes naming rules

For example:

```
{{ .Values.applicationName | quote }}
```

may produce a valid YAML string that is still an invalid Kubernetes resource name or label value.

YAML quoting and Kubernetes semantic validation are separate concerns.

# 9. String transformation functions

String functions are useful for generating labels, annotations, configuration values, and consistent names.

## 9.1 `upper`

```
{{ "production" | upper }}
```

Output:

```
PRODUCTION
```

Useful for environment-variable values and human-readable configuration.

## 9.2 `lower`

```
{{ "PAYMENTS-API" | lower }}
```

Output:

```
payments-api
```

Useful for normalization.

## 9.3 `trim`

```
{{ "  payments-api  " | trim }}
```

Output:

```
payments-api
```

Useful when input contains unintended leading or trailing whitespace.

## 9.4 `replace`

```
{{ "payments_api" | replace "_" "-" }}
```

Output:

```
payments-api
```

Useful for normalizing application identifiers.

## 9.5 `contains`

`contains` checks whether one string occurs inside another.

Syntax:

```
{{ contains "substring" "full string" }}
```

Example:

```
{{ contains "prod" "production" }}
```

Output:

```
true
```

Pipeline form:

```
{{ .Values.environment | contains "prod" }}
```

This passes the environment string as the final argument.

### Important caution

Do not use a substring check as your main environment classifier.

For example, `contains "prod"` could also match unexpected strings such as `nonproduction`.

If you need exact matching:

```
{{ eq .Values.environment "production" }}
```

For controlled environment values, a schema enum is often better.

# 10. The `printf` function

`printf` constructs formatted strings.

Example:

```
{{ printf "%s-%s" .Release.Name .Chart.Name }}
```

If:

```
Release Name: demo
Chart Name: function-lab
```

the result is:

```
demo-function-lab
```

## 10.1 Common formatting verbs

| Verb | Purpose                      |
| ---- | ---------------------------- |
| `%s` | String                       |
| `%d` | Decimal integer              |
| `%v` | Default value representation |
| `%q` | Quoted representation        |
| `%%` | Literal percent sign         |

Example:

```
{{ printf "%s-%d" .Release.Name .Values.replicaCount }}
```

Result:

```
demo-3
```

## 10.2 Generating chart labels

```
metadata:
  labels:
    helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | quote }}
```

This combines:

1. `printf` to create the chart identifier.
2. `replace` to normalize SemVer build metadata.
3. `quote` to format the YAML value.

## 10.3 Kubernetes naming limits

`printf` does not guarantee a valid Kubernetes name.

A production chart may also need:

```
{{ printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" }}
```

This is a common name-generation pattern, but the exact length and syntax restrictions depend on the Kubernetes resource field.

Avoid assuming all Kubernetes names share the same constraints.

# 11. The `toYaml` function

`toYaml` converts structured values into YAML text.

This is one of the most useful Helm functions for Kubernetes charts.

Example values:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

Template:

```
resources:
  {{- toYaml .Values.resources | nindent 2 }}
```

Rendered:

```
resources:
  limits:
    memory: 256Mi
  requests:
    cpu: 100m
    memory: 128Mi
```

The ordering of map keys may differ from the input; do not rely on the original map order.

## 11.1 Why use `toYaml`?

Without `toYaml`, you might write:

```
resources:
  requests:
    cpu: {{ .Values.resources.requests.cpu }}
    memory: {{ .Values.resources.requests.memory }}
  limits:
    memory: {{ .Values.resources.limits.memory }}
```

This is rigid.

Using `toYaml` lets chart users supply valid Kubernetes resource structures without modifying the template for each field.

## 11.2 Rendering tolerations

Values:

```
tolerations:
  - key: dedicated
    operator: Equal
    value: platform
    effect: NoSchedule
```

Template:

```
spec:
  tolerations:
    {{- toYaml .Values.tolerations | nindent 4 }}
```

Rendered:

```
spec:
  tolerations:
    - effect: NoSchedule
      key: dedicated
      operator: Equal
      value: platform
```

Again, mapping-key order is not semantically important.

## 11.3 Common misuse

Incorrect:

```
resources: {{ .Values.resources }}
```

A Go map's textual representation is not the Kubernetes YAML structure you intended.

Correct:

```
resources:
  {{- toYaml .Values.resources | nindent 2 }}
```

# 12. The `fromYaml` function

`fromYaml` parses a YAML string into a structured value that a template can access.

Conceptually:

```
YAML String
    │
    ▼
fromYaml
    │
    ▼
Dictionary / Structured Value
    │
    ▼
Template Logic
```

Example:

```
{{- $configuration := fromYaml "logLevel: info\nreplicas: 3" }}
```

You can then access:

```
{{ $configuration.logLevel }}
```

and:

```
{{ $configuration.replicas }}
```

## 12.1 Reading a chart file

Suppose:

```
function-lab/
├── files/
│   └── settings.yaml
└── templates/
    └── configmap.yaml
```

`files/settings.yaml`:

```
logging:
  level: info
  format: json

features:
  cache: true
```

Template:

```
{{- $settings := .Files.Get "files/settings.yaml" | fromYaml }}
```

Then:

```
data:
  LOG_LEVEL: {{ $settings.logging.level | quote }}
  LOG_FORMAT: {{ $settings.logging.format | quote }}
  CACHE_ENABLED: {{ $settings.features.cache | quote }}
```

## 12.2 Error-handling caution

`fromYaml` is not a substitute for validating input structure.

Malformed YAML may produce an error-bearing result rather than a normal parsed map.

When processing YAML supplied as arbitrary text, validate the expected keys and types before using them.

For ordinary chart configuration, prefer structured `values.yaml` values rather than unnecessarily converting YAML to strings and parsing it again.

# 13. `indent` and `nindent`

Both functions add indentation.

The difference is that `nindent` inserts an initial newline.

Example:

```
{{ "one\ntwo" | indent 4 }}
```

Result:

```
    one
    two
```

With:

```
{{ "one\ntwo" | nindent 4 }}
```

the output begins with a newline:

```

    one
    two
```

## 13.1 Correct nested rendering

Template:

```
spec:
  template:
    spec:
      containers:
        - name: web
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

The `resources` child keys need twelve spaces in this particular structure.

## 13.2 Incorrect indentation

```
resources:
  {{- toYaml .Values.resources | nindent 2 }}
```

This may be correct at the root level but incorrect inside a deeply nested container definition.

Indentation must be calculated from the surrounding YAML.

## 13.3 Practical rule

Use:

```
{{- toYaml VALUE | nindent N }}
```

for many nested YAML structures, where `N` is the required indentation depth.

Then inspect the rendered output rather than assuming the result is correct.

# 14. Type conversion concepts

Helm values can represent strings, numbers, booleans, lists, maps, and null values.

Functions sometimes expect a specific type.

For example:

```
{{ .Values.replicaCount | int }}
```

converts the value to an integer representation.

Other conversion helpers include:

```
{{ .Values.someValue | toString }}
```

```
{{ .Values.someValue | int64 }}
```

```
{{ .Values.someValue | float64 }}
```

## 14.1 Inspecting types

Useful functions include:

```
{{ kindOf .Values.replicaCount }}
```

```
{{ typeOf .Values.replicaCount }}
```

For example, the general kind may be `int`, `string`, `bool`, `slice`, or `map`.

## 14.2 Conversion is not validation

Suppose:

```
replicaCount: "invalid"
```

Blindly applying:

```
{{ .Values.replicaCount | int }}
```

does not guarantee a useful error.

Some conversion functions may produce zero-like results for unsupported inputs.

For a production chart, define a schema:

```
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "replicaCount": {
      "type": "integer",
      "minimum": 0
    }
  }
}
```

Save this as `values.schema.json` in the chart root.

Helm can then reject values that do not satisfy the declared schema.

## 14.3 Type-conversion principles

- Preserve native types where possible.
- Convert only when the target operation requires it.
- Do not hide malformed configuration through silent conversions.
- Validate types at the values boundary.
- Quote values according to the target Kubernetes field.

# 15. Working with lists

Lists represent ordered collections.

Example values:

```
allowedOrigins:
  - example.com
  - api.example.com
  - internal.example.com
```

A list can also be created in a template:

```
{{- $environments := list "development" "staging" "production" }}
```

Useful list functions include:

| Function  | Purpose                         |
| --------- | ------------------------------- |
| `list`    | Create a list                   |
| `first`   | First element                   |
| `rest`    | All except first                |
| `last`    | Last element                    |
| `append`  | Create list with appended item  |
| `prepend` | Create list with prepended item |
| `concat`  | Combine lists                   |
| `uniq`    | Remove duplicate entries        |
| `has`     | Check list membership           |
| `len`     | Number of elements              |

## 15.1 Example: list membership

```
{{- $supported := list "development" "staging" "production" }}
{{- if not (has .Values.environment $supported) }}
{{- fail "environment must be development, staging, or production" }}
{{- end }}
```

This checks exact membership.

It is safer than using a substring test.

## 15.2 Lists and rendering

A list of Kubernetes objects can be rendered using `toYaml`:

```
imagePullSecrets:
  {{- toYaml .Values.imagePullSecrets | nindent 2 }}
```

However, for an empty list, ensure the resulting field is appropriate for the Kubernetes schema. You may prefer to omit optional fields entirely when their collections are empty.

# 16. Working with dictionaries

A dictionary is a collection of key-value pairs.

In Helm values, dictionaries are commonly represented as YAML maps.

Example:

```
labels:
  team: platform
  environment: staging
```

A dictionary can be created in a template:

```
{{- $labels := dict "team" "platform" "environment" "staging" }}
```

Useful functions:

| Function         | Purpose                                    |
| ---------------- | ------------------------------------------ |
| `dict`           | Create dictionary                          |
| `get`            | Retrieve value by key                      |
| `hasKey`         | Check whether key exists                   |
| `set`            | Set a key                                  |
| `unset`          | Remove a key                               |
| `keys`           | Get keys                                   |
| `values`         | Get values                                 |
| `merge`          | Merge dictionaries                         |
| `mergeOverwrite` | Merge with overwrite precedence            |
| `deepCopy`       | Copy nested data                           |
| `dig`            | Traverse nested dictionaries with fallback |

## 16.1 Checking whether a key exists

```
{{ hasKey .Values "replicaCount" }}
```

This returns a boolean.

It can distinguish a missing key from a present value such as `0` or `false`.

## 16.2 Using `get`

```
{{ get .Values.labels "team" }}
```

If the key exists, the function retrieves its value.

## 16.3 Building a dictionary

```
{{- $labels := dict
    "app.kubernetes.io/name" .Chart.Name
    "app.kubernetes.io/instance" .Release.Name
    "team" "platform"
}}
```

Then:

```
metadata:
  labels:
    {{- toYaml $labels | nindent 4 }}
```

## 16.4 Dictionary mutation cautions

Functions such as `set` and `unset` can modify dictionaries.

That can make template behavior harder to understand, particularly when shared nested objects are involved.

Some merge operations also share references to nested dictionaries rather than deep-copying them.

If you need to modify merged data independently, consider using `deepCopy`.

For straightforward charts, favor clear values and direct rendering over extensive dictionary mutation.

# 17. Understanding `lookup`

`lookup` allows a Helm template to query existing Kubernetes resources.

Its conceptual syntax is:

```
{{ lookup API_VERSION KIND NAMESPACE NAME }}
```

Example:

```
{{ lookup "v1" "ConfigMap" "helm-lab" "existing-config" }}
```

This attempts to retrieve a ConfigMap from Kubernetes.

## 17.1 What makes `lookup` different?

Most Helm template functions operate only on supplied chart data.

`lookup` may depend on the current cluster state.

```
Chart + Values
      │
      ▼
Helm Template
      │
      ├── Normal Functions
      │       └── Local Data Transformation
      │
      └── lookup
              │
              ▼
        Kubernetes API
              │
              ▼
        Existing Resource Data
```

## 17.2 Rendering caveat

Ordinary offline `helm template` rendering does not perform the same live cluster lookups as a real installation.

Where supported, server-side dry-run can be used to test cluster-aware rendering:

```
helm install demo ./function-lab \
  --dry-run=server \
  --namespace helm-lab
```

Use this only with a known disposable cluster and appropriate permissions.

## 17.3 Risks of `lookup`

Permissions: The Helm identity may not have permission to read the resource.

Reproducibility: The same chart and values can render differently as cluster state changes.

Offline validation: CI pipelines without cluster access may not reproduce the same output.

GitOps behavior: Controllers may render charts under different conditions, and cluster-dependent logic can complicate reconciliation.

Missing resources: A resource may not exist during first installation.

## 17.4 Production guidance

Use `lookup` sparingly.

Prefer explicit values, stable release configuration, and declarative Kubernetes resources when possible.

Do not use `lookup` merely because it is available.

# 18. Cryptographic and random functions

Helm provides functions for hashing, random generation, certificates, and other cryptographic operations.

Examples include:

```
{{ "example" | sha256sum }}
```

```
{{ randAlphaNum 16 }}
```

Some functions can also generate certificates or keys.

## 18.1 Hashing versus randomness

A hash of the same input normally produces the same output.

A random generator produces different values across executions.

```
Deterministic Input
        │
        ▼
sha256sum
        │
        ▼
Stable Digest
```

Versus:

```
Random Generator
        │
        ▼
New Random Value
        │
        ▼
Potentially Different Manifest
```

## 18.2 Why randomness can be dangerous

Consider:

```
data:
  PASSWORD: {{ randAlphaNum 24 | b64enc | quote }}
```

If this is rendered again, a new password may be generated.

That can cause unexpected changes during upgrades or GitOps reconciliation.

It can also create differences between CI-rendered manifests and installed manifests.

## 18.3 Cryptographic data is not automatically secret-safe

Base64 encoding is not encryption.

A Kubernetes Secret containing base64-encoded data does not become securely encrypted simply because it uses `b64enc`.

Secrets may still be exposed through:

- Helm release records.
- Kubernetes API access.
- Rendered manifests.
- CI/CD logs.
- Chart artifacts or values files.

Use an appropriate secret-management system and restrict access to sensitive deployment data.

## 18.4 Production recommendation

Prefer externally managed credentials or carefully designed secret lifecycles.

Use deterministic hashes for checksums and rollout annotations where appropriate.

Avoid generating new credentials during every render.

# 19. Defensive template design

Defensive templates are designed to reject invalid configuration and produce predictable manifests.

The goal is not to make every possible value work.

The goal is to define a clear, supported configuration contract.

## 19.1 Validate mandatory settings

```
{{ required "application.name is required" .Values.application.name }}
```

## 19.2 Preserve meaningful false and zero values

Do not use `default` blindly for booleans or replica counts.

## 19.3 Validate supported options

```
{{- if not (has .Values.environment (list "development" "staging" "production")) }}
{{- fail "unsupported environment" }}
{{- end }}
```

## 19.4 Normalize string values carefully

```
{{ .Values.application.name | trim | lower | replace "_" "-" }}
```

But normalization is not full Kubernetes-name validation.

## 19.5 Render nested structures correctly

```
{{- toYaml .Values.resources | nindent 12 }}
```

## 19.6 Avoid hidden cluster dependencies

Use `lookup` only when its behavior is intentional and documented.

## 19.7 Avoid nondeterministic rendering

Do not introduce randomness into stable Kubernetes configuration without a carefully defined lifecycle.

## 19.8 Prefer schema validation for values contracts

A schema can enforce:

- Required keys.
- Types.
- Enumerated values.
- Numeric limits.
- String patterns.
- Object structures.

Template functions should complement schema validation, not replace it.

# 24. Lab 3: Build a Deployment using functions

Create `function-lab/templates/deployment.yaml`:

```
{{- $supportedEnvironments := list "development" "staging" "production" -}}
{{- if not (has .Values.environment $supportedEnvironments) -}}
{{- fail "environment must be development, staging, or production" -}}
{{- end -}}
{{- $applicationName := required "application.name is required" .Values.application.name | trim | lower | replace "_" "-" | replace " " "-" -}}
{{- $applicationID := required "application.identifier is required" .Values.application.identifier -}}
{{- $imageRepository := required "image.repository is required" .Values.image.repository -}}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ printf "%s-%s" .Release.Name $applicationID | quote }}
  labels:
    app.kubernetes.io/name: {{ $applicationID | quote }}
    app.kubernetes.io/instance: {{ .Release.Name | quote }}
    app.kubernetes.io/managed-by: {{ .Release.Service | quote }}
    environment: {{ .Values.environment | lower | quote }}
    display-name: {{ $applicationName | quote }}
    {{- with .Values.labels }}
    {{- toYaml . | nindent 4 }}
    {{- end }}

spec:
  replicas: {{ .Values.replicaCount }}

  selector:
    matchLabels:
      app.kubernetes.io/name: {{ $applicationID | quote }}
      app.kubernetes.io/instance: {{ .Release.Name | quote }}

  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ $applicationID | quote }}
        app.kubernetes.io/instance: {{ .Release.Name | quote }}
        environment: {{ .Values.environment | quote }}

      {{- with .Values.annotations }}
      annotations:
        {{- toYaml . | nindent 8 }}
      {{- end }}

    spec:
      {{- with .Values.nodeSelector }}
      nodeSelector:
        {{- toYaml . | nindent 8 }}
      {{- end }}

      {{- with .Values.tolerations }}
      tolerations:
        {{- toYaml . | nindent 8 }}
      {{- end }}

      containers:
        - name: web
          image: {{ printf "%s:%s" $imageRepository (.Values.image.tag | default .Chart.AppVersion) | quote }}
          imagePullPolicy: {{ .Values.image.pullPolicy }}

          ports:
            - name: http
              containerPort: {{ .Values.container.port }}
              protocol: TCP

          env:
            - name: ENVIRONMENT
              value: {{ .Values.environment | upper | quote }}

            - name: LOG_LEVEL
              value: {{ .Values.config.logLevel | upper | quote }}

            - name: FEATURE_ENABLED
              value: {{ .Values.config.featureEnabled | quote }}

            - name: MESSAGE
              value: {{ .Values.config.message | quote }}

          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

## Functions used

| Function   | Where                          | Why                           |
| ---------- | ------------------------------ | ----------------------------- |
| `list`     | Supported environments         | Create valid options          |
| `has`      | Environment validation         | Check membership              |
| `fail`     | Invalid environment            | Stop rendering                |
| `required` | Application and image values   | Reject missing configuration  |
| `trim`     | Application name               | Remove surrounding spaces     |
| `lower`    | Application name               | Normalize case                |
| `replace`  | Application name               | Replace separators            |
| `printf`   | Deployment name and image      | Format strings                |
| `default`  | Image tag                      | Fall back to chart appVersion |
| `quote`    | String fields                  | Preserve YAML string types    |
| `upper`    | Environment variables          | Format output                 |
| `toYaml`   | Labels, annotations, resources | Render maps                   |
| `nindent`  | Nested YAML                    | Correct indentation           |

Production note: The `display-name` label is valid for the sample input, but arbitrary application names require additional Kubernetes label-value validation. Likewise, the generated Deployment name must satisfy Kubernetes naming limits. The lab focuses on functions; a later production-hardening exercise should enforce those constraints.

# 45. Troubleshooting reference

| Symptom                              | Likely cause                              | Investigation                             |
| ------------------------------------ | ----------------------------------------- | ----------------------------------------- |
| `wrong type for value`               | Function received unexpected type         | Inspect pipeline input and function order |
| `required ...` error                 | Mandatory value empty                     | Check effective values and overrides      |
| YAML parse error                     | Indentation or quoting                    | Render with `--debug`                     |
| Invalid replica type                 | Numeric field quoted                      | Remove `quote`, validate schema           |
| Unexpected `true`                    | `default true` overriding `false`         | Use presence check or direct boolean      |
| Empty nested value                   | Missing key or wrong context              | Inspect `.Values` path and dot            |
| Map-like output instead of YAML      | Missing `toYaml`                          | Serialize structured value                |
| ConfigMap rejected                   | Non-string `data` values                  | Quote or stringify values                 |
| Resource changes every render        | Random function or cluster-dependent data | Remove nondeterminism                     |
| Offline and cluster rendering differ | `lookup` or capabilities                  | Compare rendering environments            |
| Invalid resource name                | Insufficient normalization/validation     | Enforce Kubernetes naming rules           |
| Chart renders but Pods fail          | Runtime or Kubernetes configuration issue | Inspect events, Pods, logs, probes        |

# 46. Production engineering: function design principles

A professional Helm chart should use functions intentionally.

## 46.1 Keep pipelines readable

Good:

```
{{ .Values.environment | lower | quote }}
```

Harder to maintain:

```
{{ .Values.application.name | trim | lower | replace "_" "-" | replace " " "-" | trunc 63 | trimSuffix "-" | quote }}
```

The second may be justified, but repeated complex pipelines should usually be extracted into reusable helpers.

That topic will be expanded in the later helper-template chapter.

## 46.2 Separate validation from formatting

Validation determines whether a value is acceptable.

Formatting determines how the value is rendered.

Avoid using formatting functions to conceal invalid input.

## 46.3 Do not silently override user intent

A user-provided `false`, `0`, or empty list may be intentional.

Understand how `default` and related functions interpret empty values.

## 46.4 Prefer declarative configuration

Avoid templates that depend unnecessarily on mutable cluster state.

This is especially important for GitOps and reproducible CI/CD workflows.

## 46.5 Avoid random output in stable resources

Randomness can cause unexpected updates, configuration drift, and secret rotation.

Use deterministic configuration wherever possible.

## 46.6 Validate rendered output

The final Kubernetes manifest is the actual artifact that matters.

Review it.

Test it.

Validate it against the target API.

# 47. Real-world production scenarios

## Scenario A: Image tag fallback

A platform team maintains one chart for several application versions.

Values:

```
image:
  repository: registry.example.com/payments
  tag: ""
```

Template:

```
{{ .Values.image.tag | default .Chart.AppVersion }}
```

Benefit:

The application version from chart metadata is used unless explicitly overridden.

Risk:

If chart metadata is not maintained correctly, the wrong image tag may be selected.

## Scenario B: Mandatory external endpoint

An application requires an API endpoint.

Template:

```
{{ required "externalApi.url is required" .Values.externalApi.url | quote }}
```

Benefit:

Rendering fails early rather than deploying a broken configuration.

Risk:

A nonempty but malformed URL still passes. Add schema validation.

## Scenario C: Environment validation

A platform supports only:

```
development
staging
production
```

A chart validates environment membership using `has`.

Benefit:

Unsupported environment values fail before deployment.

Risk:

Duplicating validation logic across many templates creates maintenance overhead. Prefer a schema or a centralized validation helper.

## Scenario D: ConfigMap generation

A chart accepts structured configuration:

```
applicationConfig:
  logging:
    level: info
  cache:
    enabled: true
```

Template:

```
data:
  application.yaml: |
    {{- toYaml .Values.applicationConfig | nindent 4 }}
```

Benefit:

Applications can receive a complete configuration document.

Risk:

The chart still needs to validate that the supplied structure is meaningful for the application.

## Scenario E: Random password generation

A chart generates a random password during every render.

Benefit:

Initial credential creation appears convenient.

Risk:

Repeated rendering may generate different credentials, causing application outages or configuration drift.

A managed secret lifecycle is safer.
