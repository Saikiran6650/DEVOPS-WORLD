# PART 4: HELM VALUES AND CONFIGURATION


## Goal

Understand how Helm values make charts reusable, configurable, and suitable for deployment across development, staging, and production environments.

In Part 3, you learned how Helm charts are structured. You created a chart, examined `Chart.yaml`, explored `values.yaml`, studied templates, and rendered Kubernetes manifests.

In Part 4, you will learn how to turn a chart into a reusable deployment interface.

Instead of modifying Kubernetes templates whenever an environment changes, you will define configuration values, override them safely, validate their types, and manage environment-specific settings.

You will build one application chart that can produce different Kubernetes configurations for three environments without duplicating the Deployment and Service templates.

By the end, you should be able to explain:

```
One Helm Chart
+
Default Values
+
Environment Values
+
Optional CLI Overrides
↓
Helm Rendering
↓
Environment-Specific Kubernetes Manifests
```

You will also learn why values management is not simply a matter of placing variables in YAML. Poor values design can introduce unexpected behavior, configuration drift, security problems, and failed production deployments.

By the end of this chapter, you should be able to:

15. Apply production standards to Helm configuration management.

# 2. The problem Helm values solve

Consider a Kubernetes application deployed to three environments.

Development:

```
replicas: 1
```

Staging:

```
replicas: 2
```

Production:

```
replicas: 4
```

The application uses the same Deployment structure in every environment.

Only the configuration changes.

Without configuration abstraction, teams may create separate files:

```
kubernetes/
├── development/
│   ├── deployment.yaml
│   └── service.yaml
├── staging/
│   ├── deployment.yaml
│   └── service.yaml
└── production/
    ├── deployment.yaml
    └── service.yaml
```

The three Deployment files may be almost identical.

This creates several problems.

Duplication: The same configuration structure exists in multiple places.

Inconsistent changes: A security improvement may be applied to production but forgotten in staging.

Maintenance overhead: Updating container ports, probes, or labels requires editing multiple files.

Configuration drift: Environments gradually diverge in ways that are not intentional.

Review difficulty: Pull requests contain repeated YAML rather than the actual differences between environments.

Helm values solve this by separating deployment structure from deployment configuration.

One reusable chart

Deployment and Service templates

Development

Replicas: 1

CPU: 100m

Staging

Replicas: 2

CPU: 200m

Production

Replicas: 4

CPU: 500m

Three environment-specific rendered manifests

Same templates, different configuration

This is the central purpose of Helm values.

# 3. Understanding `.Values`

`.Values` is a built-in object available inside Helm templates.

It provides access to the configuration values used when rendering a chart.

For example, suppose `values.yaml` contains:

```
replicaCount: 2
```

Your Deployment template can reference:

```
spec:
  replicas: {{ .Values.replicaCount }}
```

Helm renders:

```
spec:
  replicas: 2
```

The important relationship is:

```
values.yaml
    │
    ▼
.Values.replicaCount
    │
    ▼
Helm template engine
    │
    ▼
replicas: 2
```

## 3.1 What the leading dot means

In Helm templates:

```
.Values.replicaCount
```

the leading dot refers to the current template context.

At the chart's top-level template context, `.Values` provides access to chart values.

However, the meaning of `.` can change inside constructs such as `with` and `range`.

For example:

```
{{- with .Values.image }}
repository: {{ .repository }}
{{- end }}
```

Inside the `with` block, the dot refers to the `image` map.

You will explore template scoping in more detail in the templating chapter.

For now, understand that `.Values` is the primary configuration interface.

## 3.2 Where values come from

Values can come from several sources:

- The chart's default `values.yaml`.
- Values files supplied by the user.
- Command-line overrides.
- Values passed programmatically by tools that invoke Helm.
- Parent charts, when working with chart dependencies.

For this chapter, you will concentrate on the first three.

## 3.3 Values are not Kubernetes resources

Consider:

```
monitoring:
  enabled: true
```

Adding this to `values.yaml` does not automatically create a monitoring resource.

A template must reference the value.

For example:

```
{{- if .Values.monitoring.enabled }}
# Monitoring resource template goes here
{{- end }}
```

The value influences rendering only when the chart uses it.

This distinction prevents a common misunderstanding:

Values are configuration inputs, not automatic Kubernetes instructions.

# 4. Default values

Every application chart can provide default configuration in `values.yaml`.

Example:

```
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

These values form the chart's default behavior.

If you run:

```
helm template demo ./my-chart
```

without providing additional configuration, Helm uses the chart defaults.

## 4.1 Why defaults matter

Good defaults make a chart easier to use.

A developer should be able to understand the intended baseline without supplying dozens of values.

However, defaults must also be safe.

For example, consider:

```
service:
  type: LoadBalancer
```

If this is the default, installing the chart on a supported cloud cluster may create an externally provisioned load balancer.

For an internal application, that may be unnecessary or undesirable.

A safer general-purpose default is often:

```
service:
  type: ClusterIP
```

Likewise, do not enable public Ingress routing by default unless that is explicitly the chart's intended behavior.

## 4.2 Defaults are not production policy

A default value is not necessarily an appropriate production value.

For example:

```
replicaCount: 1
```

may be suitable for a disposable lab but insufficient for a highly available production service.

Production configuration should be explicit and reviewed.

# 5. Nested values

Helm values can be organized into nested structures.

Example:

```
image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent
```

Template references:

```
{{ .Values.image.repository }}
```

```
{{ .Values.image.tag }}
```

```
{{ .Values.image.pullPolicy }}
```

A Deployment might contain:

```
containers:
  - name: nginx
    image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
    imagePullPolicy: {{ .Values.image.pullPolicy }}
```

Rendered output:

```
containers:
  - name: nginx
    image: "nginx:1.27"
    imagePullPolicy: IfNotPresent
```

## 5.1 Why nesting helps

Compare these two approaches.

Flat configuration:

```
imageRepository: nginx
imageTag: "1.27"
imagePullPolicy: IfNotPresent
serviceType: ClusterIP
servicePort: 80
```

Grouped configuration:

```
image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

Both can work.

The grouped approach becomes easier to maintain as related settings increase.

It also makes the configuration interface easier to understand.

## 5.2 Avoid excessive nesting

This is technically possible:

```
application:
  deployment:
    container:
      image:
        configuration:
          repository: nginx
```

But it makes ordinary configuration cumbersome:

```
{{ .Values.application.deployment.container.image.configuration.repository }}
```

Nested structures should reflect meaningful groups, not arbitrary hierarchy.

# 6. YAML value types

YAML supports several data types relevant to Helm configuration.

Understanding these types is essential because Helm templates ultimately generate Kubernetes resources with specific type requirements.

| Type    | Example                | Common use                     |
| ------- | ---------------------- | ------------------------------ |
| String  | `"nginx"`              | Image names, hostnames, labels |
| Integer | `3`                    | Replica counts, ports          |
| Boolean | `true`                 | Feature switches               |
| List    | `["a", "b"]`           | Arguments, tolerations, hosts  |
| Map     | `image: {tag: "1.27"}` | Grouped configuration          |
| Null    | `null`                 | Explicit absence of a value    |

Let's examine them individually.

# 7. Strings

A string represents text.

Example:

```
applicationName: "web"
```

Other examples:

```
environment: "development"
imageTag: "1.27"
hostname: "app.example.com"
```

Template:

```
metadata:
  labels:
    environment: {{ .Values.environment | quote }}
```

Rendered:

```
metadata:
  labels:
    environment: "development"
```

## Why quoting matters

Kubernetes labels and annotations require string values.

For example:

```
metadata:
  labels:
    build: "123"
```

is appropriate.

But:

```
metadata:
  labels:
    build: 123
```

may be rejected because the value is parsed as a number.

Use `quote` when the output must be a string.

# 8. Integers

Integers are whole numbers.

Example:

```
replicaCount: 3
```

Template:

```
replicas: {{ .Values.replicaCount }}
```

Rendered:

```
replicas: 3
```

Do not automatically quote numeric fields.

Incorrect:

```
replicas: "{{ .Values.replicaCount }}"
```

This renders:

```
replicas: "3"
```

Kubernetes expects an integer for Deployment replicas, not a string.

The rendered YAML may be syntactically valid while failing Kubernetes schema validation.

Rule: Preserve the type required by the Kubernetes API.

# 9. Booleans

Booleans represent true or false.

Example:

```
ingress:
  enabled: false
```

Template:

```
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
# ...
{{- end }}
```

When `enabled` is false, the conditional block does not render.

When true, the block renders.

## Boolean quoting mistake

Consider:

```
ingress:
  enabled: "false"
```

This is a string, not a boolean.

In Helm template conditions, a nonempty string is truthy.

Therefore:

```
{{- if .Values.ingress.enabled }}
```

may evaluate as true even though the text says `"false"`.

This can unexpectedly enable a resource.

Correct:

```
ingress:
  enabled: false
```

This is one of the most important YAML type problems to understand.

# 10. Lists

Lists represent ordered collections.

Example:

```
allowedHosts:
  - app.example.com
  - api.example.com
```

Another example:

```
containerArgs:
  - "--log-level=info"
  - "--port=8080"
```

A Helm template can render a list using `toYaml`.

Example:

```
args:
{{- toYaml .Values.containerArgs | nindent 2 }}
```

Rendered:

```
args:
  - --log-level=info
  - --port=8080
```

The `toYaml` function converts the value into YAML.

The `nindent` function adds a newline and indents the output.

Indentation matters because Kubernetes manifests are YAML documents.

## List replacement behavior

When values are overridden, lists are generally replaced rather than merged item by item.

Suppose defaults contain:

```
allowedHosts:
  - app.example.com
  - api.example.com
```

An override contains:

```
allowedHosts:
  - staging.example.com
```

The resulting list is:

```
allowedHosts:
  - staging.example.com
```

It does not automatically append the staging host to the original list.

This is important for lists such as tolerations, environment variables, and Ingress hosts.

# 11. Maps and nested objects

Maps store key-value pairs.

Example:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

This is a nested map.

You can reference individual fields:

```
{{ .Values.resources.requests.cpu }}
```

Or render the complete structure:

```
resources:
{{- toYaml .Values.resources | nindent 12 }}
```

The indentation depends on where the block appears in the template.

Rendered output:

```
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

## Why maps are useful

Maps are appropriate when a value represents a structured Kubernetes configuration.

For example:

```
nodeSelector:
  kubernetes.io/os: linux
```

Or:

```
podAnnotations:
  example.com/team: platform
```

A chart can expose these as configurable maps.

However, not every Kubernetes field should automatically become a value.

You will examine that trade-off later.

# 12. Quoting in Helm templates

Quoting is not simply a formatting preference.

It affects the type of the rendered YAML.

Consider these cases.

| Kubernetes field           | Expected type | Typical template                                                       |
| -------------------------- | ------------- | ---------------------------------------------------------------------- |
| Deployment replicas        | Integer       | `{{ .Values.replicaCount }}`                                           |
| Service port               | Integer       | `{{ .Values.service.port }}`                                           |
| Container image            | String        | `{{ .Values.image.repository }}:{{ .Values.image.tag }}` inside quotes |
| Label value                | String        | `{{ .Values.environment \\| quote }}`                                  |
| Environment variable value | String        | `{{ .Values.config.logLevel \\| quote }}`                              |
| Boolean security field     | Boolean       | `{{ .Values.security.readOnlyRootFilesystem }}`                        |

For example, container environment variables expect string values:

```
env:
  - name: MAX_CONNECTIONS
    value: {{ .Values.config.maxConnections | quote }}
```

If:

```
config:
  maxConnections: 100
```

the rendered output becomes:

```
env:
  - name: MAX_CONNECTIONS
    value: "100"
```

That is correct for the Kubernetes `EnvVar.value` field.

The value can be numeric in Helm configuration but must be a string in the Kubernetes environment-variable definition.

# 13. YAML type problems

YAML's automatic type interpretation can create surprising behavior.

Consider:

```
image:
  tag: 1.20
```

The value may be interpreted as a number rather than a string.

It may lose the formatting you intended.

Prefer:

```
image:
  tag: "1.20"
```

This preserves the tag as text.

## 13.1 Numeric-looking strings

Always consider quoting:

```
version: "01"
buildNumber: "000123"
imageTag: "1.20"
```

when the values are identifiers rather than numbers used for arithmetic.

## 13.2 Boolean-looking strings

Prefer explicit strings when text is intended:

```
featureLabel: "true"
```

But use booleans for feature switches:

```
featureEnabled: true
```

## 13.3 Null values

Consider:

```
service:
  annotations: null
```

This differs from:

```
service:
  annotations: {}
```

The first represents null.

The second represents an empty map.

Helm's values merging and template logic may treat them differently.

## 13.4 Empty values

A template may use:

```
{{ .Values.image.tag | default .Chart.AppVersion }}
```

This is convenient, but you should understand that Helm's `default` function treats several values as empty, including `0`, `false`, empty strings, empty collections, and null.

This can cause problems.

For example:

```
{{ .Values.feature.enabled | default true }}
```

does not reliably preserve an explicitly supplied `false`, because `false` is considered empty.

For boolean configuration, use explicit presence checks or design defaults so that an intentional `false` is preserved.

# 14. Helm values precedence

Helm combines configuration from different sources.

The core mental model is:

```
Chart Defaults
      ↓
First Values File
      ↓
Additional Values Files
      ↓
Command-Line Overrides
      ↓
Final Effective Values
```

The later source has higher precedence for conflicting values.

A practical example:

Default `values.yaml`:

```
replicaCount: 2
```

Development file:

```
replicaCount: 1
```

Command-line override:

```
--set replicaCount=3
```

Final result:

```
replicaCount: 3
```

## Important nuance: Merging maps

Helm generally merges maps recursively.

For example, defaults:

```
image:
  repository: nginx
  tag: "1.27"
```

Override:

```
image:
  tag: "1.28"
```

Effective values:

```
image:
  repository: nginx
  tag: "1.28"
```

The repository remains because the override only changed the nested tag.

Lists and scalar values, however, are replaced by higher-precedence values.

This distinction is essential when designing environment configuration.

# 15. The `-f` flag

The `-f` flag loads a values file.

Example:

```
helm template demo ./my-chart \
  -f values-dev.yaml
```

Helm starts with the chart defaults and applies the supplied file.

If both contain the same key, the supplied file takes precedence.

Example:

Default:

```
replicaCount: 2
```

Development:

```
replicaCount: 1
```

Render:

```
helm template demo ./my-chart \
  -f values-dev.yaml
```

Result:

```
replicas: 1
```

The chart template remains unchanged.

# 16. The `--values` flag

`--values` is the long form of `-f`.

These are equivalent:

```
helm template demo ./my-chart \
  -f values-dev.yaml
```

```
helm template demo ./my-chart \
  --values values-dev.yaml
```

Use whichever is more readable for your workflow.

In CI/CD pipelines, long flags can make commands easier to understand.

For example:

```
helm upgrade --install payments ./charts/payments \
  --namespace payments \
  --values environments/production.yaml
```

The explicit flag communicates intent clearly.

# 17. Multiple values files

You can provide multiple values files.

Example:

```
helm template demo ./my-chart \
  -f values-common.yaml \
  -f values-production.yaml
```

The later file takes precedence for conflicts.

Suppose:

`values-common.yaml`:

```
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80
```

`values-production.yaml`:

```
replicaCount: 4

image:
  tag: "1.28"
```

Effective values:

```
replicaCount: 4

image:
  repository: nginx
  tag: "1.28"

service:
  type: ClusterIP
  port: 80
```

The production file overrides the replica count and image tag.

The other values remain.

## File ordering matters

Compare:

```
helm template demo ./my-chart \
  -f values-common.yaml \
  -f values-production.yaml
```

with:

```
helm template demo ./my-chart \
  -f values-production.yaml \
  -f values-common.yaml
```

These commands can produce different results.

Always establish a consistent file ordering convention.

# 18. The `--set` flag

`--set` provides command-line values.

Example:

```
helm template demo ./my-chart \
  --set replicaCount=3
```

Nested value:

```
helm template demo ./my-chart \
  --set image.tag=1.28
```

Multiple values:

```
helm template demo ./my-chart \
  --set replicaCount=3 \
  --set image.repository=nginx \
  --set image.tag=1.28
```

You can also provide comma-separated assignments, although separate flags are often easier to read.

## When `--set` helps

It is useful for:

- Quick lab experiments.
- Small deployment overrides.
- CI/CD-provided image versions.
- Testing a particular configuration.

## When `--set` becomes problematic

Avoid enormous deployment commands such as:

```
helm upgrade --install demo ./my-chart \
  --set replicaCount=4 \
  --set service.port=8080 \
  --set resources.requests.cpu=500m \
  --set resources.requests.memory=512Mi \
  --set resources.limits.memory=1Gi
```

This may work, but it becomes harder to review, audit, and reproduce.

For substantial configuration, prefer version-controlled values files.

# 19. The `--set-string` flag

`--set-string` forces a value to be treated as a string.

Example:

```
helm template demo ./my-chart \
  --set-string image.tag=1.20
```

This is useful because image tags are identifiers, not numeric quantities.

Compare:

```
--set image.tag=1.20
```

with:

```
--set-string image.tag=1.20
```

The second makes your intended string type explicit.

## Common use cases

```
--set-string image.tag=00123
```

```
--set-string config.buildId=000045
```

```
--set-string config.featureLabel=false
```

The last example intentionally passes the text `"false"`.

It should not be used when the chart expects a boolean feature switch.

For boolean settings, prefer:

```
--set ingress.enabled=false
```

# 20. Other value-setting mechanisms

Modern Helm versions provide additional ways to supply values.

Check your installed version's help output for exact support.

## 20.1 `--set-file`

`--set-file` reads a value from a file.

For example, suppose you have:

```
config/application.properties
```

Containing:

```
LOG_LEVEL=info
FEATURE_X=true
```

You can render:

```
helm template demo ./my-chart \
  --set-file applicationConfig=config/application.properties
```

The file contents become the value of `applicationConfig`.

The chart must contain a template that uses that value.

This is useful for embedding larger configuration text.

However, avoid using this mechanism to put plaintext production secrets into release manifests.

## 20.2 `--set-json`

`--set-json` allows structured JSON values to be supplied from the command line.

Example:

```
helm template demo ./my-chart \
  --set-json 'allowedHosts=["app.example.com","api.example.com"]'
```

This is useful for lists and maps that would otherwise be cumbersome to express.

## 20.3 `--set-literal`

Where supported, `--set-literal` treats the supplied content as a literal string.

This is useful when special characters should not be interpreted using the usual value parsing rules.

Because flag availability and exact parsing behavior can vary by Helm version, verify:

```
helm template --help
```

## 20.4 Repeated command-line overrides

If the same key is supplied multiple times, the later applicable override wins.

For example:

```
helm template demo ./my-chart \
  --set replicaCount=2 \
  --set replicaCount=5
```

The effective replica count is `5`.

Avoid repeated conflicting overrides in production pipelines.

They make the actual configuration harder to understand.

# 21. Choosing the right override mechanism

| Mechanism           | Best use                           |
| ------------------- | ---------------------------------- |
| `values.yaml`       | Stable chart defaults              |
| `-f` / `--values`   | Environment-specific configuration |
| Multiple `-f` files | Layered configuration              |
| `--set`             | Small typed CLI overrides          |
| `--set-string`      | Explicit string overrides          |
| `--set-file`        | Load text content from a file      |
| `--set-json`        | Structured JSON values             |
| `--set-literal`     | Literal strings, where supported   |

For production deployments, a strong baseline is:

```
Chart Defaults
+
Version-Controlled Environment Values
+
Small, Explicit Pipeline Overrides
```

Do not build an entire production configuration out of dozens of untracked command-line flags.

# 22. Environment configuration strategy

A common chart repository layout is:

```
helm-learning/
├── charts/
│   └── web-app/
│       ├── Chart.yaml
│       ├── values.yaml
│       └── templates/
│           ├── deployment.yaml
│           └── service.yaml
└── environments/
    ├── values-dev.yaml
    ├── values-staging.yaml
    └── values-production.yaml
```

This structure separates the reusable chart from environment-specific settings.

Another valid approach is to store environment values within the chart repository.

The most important requirement is consistency and clear ownership.

## Environment responsibilities

| Environment | Primary goal                   | Typical configuration                        |
| ----------- | ------------------------------ | -------------------------------------------- |
| Development | Fast iteration                 | Lower replica count, smaller resources       |
| Staging     | Production-like validation     | Similar behavior to production               |
| Production  | Reliable user-facing operation | Capacity, availability, security, monitoring |

Do not assume production should differ from staging in every setting.

Staging should be sufficiently representative to validate meaningful production behavior.

# 23. Development values

Example:

```
replicaCount: 1

image:
  repository: nginx
  tag: "1.27"

  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: 50m
    memory: 64Mi
  limits:
    memory: 128Mi

config:
  logLevel: debug
```

Development often prioritizes low cost and ease of iteration.

However, even development configuration should be valid, reproducible, and understandable.

# 24. Staging values

Example:

```
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi

config:
  logLevel: info
```

Staging should help you detect issues before production.

It should exercise the same chart structure and important operational behavior.

# 25. Production values

Example:

```
replicaCount: 4

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    memory: 512Mi

config:
  logLevel: warn
```

These are illustrative lab values, not universal production sizing recommendations.

Real resource requests and limits must be determined from workload measurements and operational requirements.

Production configuration should also consider:

```
High availability
Health probes
Security context
Autoscaling
Disruption budgets
Topology distribution
Monitoring
Secrets
Network policies
```

Those features belong in later, more advanced chart design and production engineering chapters.

# 26. Hands-on project: Build a configurable Helm chart

You will now build on the minimal chart from Part 3.

We will use the following working directory:

```
helm-learning/
```

If you still have:

```
minimal-web/
```

from Part 3, copy it:

```
cp -R minimal-web configurable-web
```

If you no longer have it, recreate the basic chart structure:

```
mkdir -p configurable-web/templates
```

Your target structure is:

```
helm-learning/
├── configurable-web/
│   ├── Chart.yaml
│   ├── values.yaml
│   └── templates/
│       ├── deployment.yaml
│       └── service.yaml
└── environments/
    ├── values-dev.yaml
    ├── values-staging.yaml
    └── values-production.yaml
```

```
    app.kubernetes.io/name: configurable-web

  replicas: {{ .Values.replicaCount }}
```

# 44. Good values API design

A chart's values are its public configuration interface.

Good values should be:

- Understandable.
- Consistent.
- Predictable.
- Documented.
- Typed appropriately.
- Safe by default.
- Stable across compatible chart versions.

Consider:

```
replicaCount: 3

image:
  repository: registry.example.com/payments
  tag: "2.4.1"

service:
  port: 8080

resources:
  requests:
    cpu: 250m
    memory: 256Mi
```

The configuration is grouped by responsibility.

A chart user can understand what each setting controls.

## Good naming

Prefer:

```
replicaCount: 3
```

over:

```
r: 3
```

Prefer:

```
image:
  pullPolicy: IfNotPresent
```

over:

```
imgPull: IfNotPresent
```

Avoid abbreviations that save a few characters but reduce clarity.

# 45. Bad values API design

Consider:

```
a: 3
b: nginx
c: 80
d: true
```

This is difficult to understand.

Another problematic design:

```
deployment:
  spec:
    template:
      spec:
        containers:
          - name: nginx
            image: nginx
```

This may simply expose a large portion of raw Kubernetes configuration without providing meaningful chart abstractions.

There are situations where passing through Kubernetes structures is appropriate.

But blindly reproducing the entire Kubernetes API as values can make the chart harder to maintain.

The purpose of Helm is not to turn every YAML field into a configurable variable.

# 46. Over-parameterization

Over-parameterization occurs when a chart exposes too many unnecessary settings.

Imagine a chart with hundreds of values for a simple application.

Users must understand all those settings before they can safely deploy.

Problems include:

```
Complex configuration
Unclear defaults
More invalid combinations
Harder documentation
More testing requirements
Higher maintenance cost
```

Example:

```
deployment:
  metadata:
    customNamePrefix: ""
    customNameSuffix: ""
    customLabelPrefix: ""
    customAnnotationPrefix: ""
```

If the application has no real need for these options, they introduce unnecessary complexity.

## When to expose a value

Ask:

1. Will different environments legitimately need different settings?
2. Is the setting safe for users to change?
3. Can the chart validate the value?
4. Is the behavior documented?
5. Will supporting this value create long-term compatibility obligations?

Expose values deliberately.

# 47. Under-parameterization

Under-parameterization is the opposite problem.

A chart hardcodes settings that users reasonably need to change.

Example:

```
spec:
  replicas: 2
```

If development and production require different replica counts, hardcoding this value forces template modification or chart duplication.

Another example:

```
image: nginx:1.27
```

If the chart is used for multiple application versions, the image tag should usually be configurable.

A better approach:

```
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

The goal is balance.

Expose configuration that varies intentionally. Keep internal implementation details internal unless there is a clear need to expose them.

# 48. Required configuration

Not every value should have a default.

Some configuration must be explicitly supplied by the deployment environment.

Examples:

```
External API endpoint
Tenant identifier
Required domain name
Cloud resource identifier
Application-specific connection setting
```

A chart can enforce required values.

## 48.1 Using `required`

Example:

```
{{ required "config.apiEndpoint is required" .Values.config.apiEndpoint }}
```

If the value is missing or empty, Helm fails rendering with the specified message.

A ConfigMap template might use:

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-config
data:
  API_ENDPOINT: {{ required "config.apiEndpoint is required" .Values.config.apiEndpoint | quote }}
```

Then the values file must supply:

```
config:
  apiEndpoint: "https://api.example.com"
```

## Important design consideration

Do not use `required` indiscriminately.

A chart that requires dozens of unrelated values can become difficult to use.

Required values should reflect genuine deployment requirements.

# 49. Values schema validation

Helm supports values validation using a JSON Schema file named:

```
values.schema.json
```

This allows you to define expected types and constraints.

Example:

```
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "replicaCount": {
      "type": "integer",
      "minimum": 1
    },
    "image": {
      "type": "object",
      "properties": {
        "repository": {
          "type": "string",
          "minLength": 1
        },
        "tag": {
          "type": "string",
          "minLength": 1
        }
      },
      "required": ["repository", "tag"]
    }
  },
  "required": ["replicaCount", "image"]
}
```

This schema requires:

```
replicaCount → Integer >= 1
image.repository → Nonempty string
image.tag → Nonempty string
```

If a user supplies:

```
replicaCount: "three"
```

Helm can reject the values during validation.

## Why schemas matter

Without a schema, an invalid type may reach the rendered Kubernetes manifest.

With a schema, you can detect the problem earlier.

```
Invalid Values
↓
Schema Validation
↓
Fail Early
```

This is especially valuable in automated deployment pipelines.

# 51. Diagnosing quoting errors

Consider:

```
replicaCount: "3"
```

This is a string.

The Deployment expects an integer.

If the template renders:

```
replicas: {{ .Values.replicaCount }}
```

the output may appear as:

```
replicas: 3
```

which is parsed as an integer in the final YAML.

However, relying on accidental coercion is poor configuration design.

A values schema makes the intended input type explicit.

Now consider:

```
replicaCount: three
```

Rendered:

```
replicas: three
```

The Kubernetes API will reject this because replicas must be numeric.

The lesson is:

Validate input types rather than relying on how YAML happens to render them.

# 52. Diagnosing boolean errors

Suppose:

```
featureEnabled: "false"
```

and your template uses:

```
{{- if .Values.featureEnabled }}
```

The string `"false"` is nonempty.

The condition may evaluate as true.

This is not the same as:

```
featureEnabled: false
```

which is a boolean.

## Corrective action

Define the expected type in `values.schema.json`:

```
{
  "featureEnabled": {
    "type": "boolean"
  }
}
```

Then reject string values when the chart expects booleans.

# 53. Diagnosing missing nested values

Suppose the template contains:

```
{{ .Values.image.repository }}
```

but the supplied configuration removes or nulls the `image` map.

The template may fail when it attempts to access the nested field.

Use:

```
helm template web ./configurable-web \
  --debug
```

Inspect the error and determine which value path is missing.

Possible solutions include:

- Provide a safe default.
- Enforce the value with a schema.
- Use a suitable template guard.
- Use `required` where appropriate.
- Avoid allowing the parent map to become null.

The right solution depends on whether the value is optional or mandatory.

# 54. Diagnosing indentation problems

YAML indentation is significant.

Consider:

```
resources:
{{ toYaml .Values.resources }}
```

Depending on placement, this may produce invalid YAML.

A safer pattern inside a container definition is:

```
resources:
  {{- toYaml .Values.resources | nindent 12 }}
```

The number of spaces must match the nesting level of the surrounding YAML.

For example:

```
containers:
  - name: nginx
    resources:
      requests:
        cpu: 100m
```

The resource structure must be nested under the container.

Helm's `toYaml` and `nindent` functions are common tools for rendering structured values correctly.

# 56. Values and release upgrades

Values management becomes especially important during upgrades.

Consider an installed release that previously used:

```
replicaCount: 4
```

A new chart version has a default of:

```
replicaCount: 2
```

The effective values during an upgrade depend on the Helm command, supplied files, and value reuse/reset behavior.

Helm provides flags such as:

```
--reuse-values
--reset-values
--reset-then-reuse-values
```

Support and exact semantics should be checked against your installed Helm version.

Do not assume that every upgrade automatically preserves every previous override or automatically resets to new chart defaults.

For production upgrades, explicitly define your values strategy and inspect the planned rendered manifests.

# 57. Configuration drift

Configuration drift occurs when environments or releases differ in unintended ways.

Example:

```
Git repository:
replicaCount: 4

Live Helm release:
replicaCount: 2
```

Possible causes:

- Someone used `--set replicaCount=2`.
- A pipeline used the wrong values file.
- A release reused old values.
- An environment file was not updated.
- A manual Helm upgrade bypassed the approved workflow.

## Production approach

Treat Git as the authoritative source for intended configuration when using a Git-managed deployment workflow.

A typical flow:

```
Configuration Change
↓
Git Commit
↓
Pull Request
↓
Validation
↓
Review
↓
Approval
↓
Deployment
↓
Verification
```

Manual CLI overrides should be controlled, documented, and minimized.

# 58. Values and secrets

Helm values are not inherently secret.

For example:

```
database:
  password: "my-password"
```

is not safe merely because it is stored in `values.yaml`.

Helm release information can contain supplied values and rendered manifests.

Users with sufficient Kubernetes access may be able to retrieve that information.

Avoid placing plaintext production secrets in:

```
values.yaml
values-production.yaml
Helm command history
CI logs
Rendered manifest artifacts
```

## Better production patterns

Use appropriate secret-management systems and deployment workflows.

Examples include:

```
External secret managers
Kubernetes Secrets managed through approved workflows
External Secrets Operator
Cloud workload identity
Encrypted secret workflows
```

Helm may reference the name of a Secret rather than containing the secret value itself.

Example:

```
database:
  existingSecret: payments-database-credentials
```

The application chart can reference the existing Kubernetes Secret.

This keeps the secret value outside ordinary chart configuration.

Remember that Kubernetes Secrets require appropriate access control and encryption practices; base64 encoding is not encryption.

# 59. Values and production reliability

Configuration changes can affect availability.

Examples:

Replica count: Reducing replicas may reduce capacity or availability.

Resource requests: Increasing requests may prevent Pods from scheduling if the cluster lacks capacity.

Memory limits: Setting limits too low may cause out-of-memory termination.

Service ports: Incorrect ports can break application connectivity.

Image tags: Incorrect tags can cause image pull failures.

Feature flags: Enabling unsupported behavior may cause runtime errors.

This means values files deserve the same review discipline as application code.

A values-only pull request can still cause a production outage.

# 60. Production configuration review checklist

Before deploying a values change, review:

- Is the correct chart version selected?
- Is the correct environment values file used?
- Are CLI overrides intentional?
- Are value types correct?
- Are required fields present?
- Are image references correct?
- Are replicas appropriate?
- Are resource requests and limits reasonable?
- Are service ports consistent with container ports?
- Are feature flags appropriate for the environment?
- Are secrets handled outside plaintext configuration?
- Does the chart pass linting?
- Do the rendered manifests pass validation?
- Have the differences from the current release been reviewed?
- Is there a rollback or recovery plan?

This checklist is particularly important for production configuration changes.

# 67. Failure scenarios and troubleshooting

## Scenario 1: Wrong values file

Symptom: Production renders with development resource settings.

Possible cause:

```
-f environments/values-dev.yaml
```

was supplied instead of:

```
-f environments/values-production.yaml
```

Diagnosis: Inspect the deployment command and rendered manifest.

Prevention: Use explicit environment selection in the deployment pipeline.

## Scenario 2: String instead of boolean

Symptom: A feature renders as enabled even though the value says `"false"`.

Cause: The value is a nonempty string.

Fix: Use an actual boolean and validate with a schema.

## Scenario 3: Image tag interpreted incorrectly

Symptom: An image reference differs from the intended tag.

Cause: A numeric-looking tag was not treated as a string.

Fix: Quote the tag in YAML or use `--set-string`.

## Scenario 4: Missing required value

Symptom: Helm rendering fails.

Cause: A required configuration value is absent.

Fix: Supply the value and validate the chart's configuration contract.

## Scenario 5: Resource requests too large

Symptom: Pods remain Pending after deployment.

Cause: Requested resources exceed available schedulable capacity or conflict with cluster policy.

Diagnosis:

```
kubectl describe pod POD_NAME \
  --context kind-helm-lab \
  -n helm-lab
```

Look for scheduling events.

Fix: Correct sizing or add appropriate capacity.

## Scenario 6: Incorrect Service port

Symptom: The application runs but Service traffic fails.

Cause: Port configuration does not match the intended application listener.

Fix: Verify the Service, target port, container port, and actual application listening port.

## Scenario 7: CLI override unexpectedly wins

Symptom: A value in Git appears correct, but the live release differs.

Cause: A command-line override was supplied during deployment.

Fix: Inspect release values and the pipeline invocation.

# 71. Advanced production considerations

## 71.1 Image digests

Image tags are convenient but may be mutable.

For stronger deployment reproducibility, production systems often pin images by digest.

Example:

```
image:
  repository: registry.example.com/payments
  digest: "sha256:..."
```

A chart must explicitly support digest-based image references if this configuration is intended.

Do not assume every chart automatically supports both tags and digests.

## 71.2 Immutable configuration promotion

A production deployment should ideally promote a tested artifact rather than rebuilding a different artifact for each environment.

Conceptually:

```
Build Application
↓
Produce Immutable Image
↓
Test in Development
↓
Validate in Staging
↓
Promote Same Artifact
↓
Deploy to Production
```

Environment values can differ while the application artifact remains the same.

## 71.3 Environment parity

Avoid unnecessary differences between staging and production.

For example, if production uses special scheduling or security settings, staging should exercise comparable behavior where practical.

Otherwise, staging may fail to reveal production-specific problems.

## 71.4 Configuration ownership

Application teams may own application settings.

Platform teams may own cluster-level constraints and deployment standards.

Security teams may define policy requirements.

The values interface should make those responsibilities clear.
