# 1. The core Helm chart mental model

A Helm chart is a structured package of files used to describe a Kubernetes application or reusable deployment components.

The most important relationship is:

Helm Chart

Chart.yaml · values.yaml · templates/ · charts/

Helm template engine

Rendered Kubernetes YAML

Deployment · Service · ConfigMap · other resources

Kubernetes API

Validates and stores the submitted resources

Kubernetes Workloads

Controllers · Pods · Services · application

The distinction is fundamental:

A Helm chart is not itself a Kubernetes Deployment.

A chart contains metadata, configuration values, and templates that Helm can use to produce Kubernetes resource manifests.

Helm manages the chart's release lifecycle. Kubernetes manages the resulting resources and workloads.

# 3. What is inside a Helm chart?

A chart is usually represented by a directory containing specially named files and folders.

For example:

```
my-chart/
├── Chart.yaml
├── values.yaml
├── charts/
├── templates/
│   ├── NOTES.txt
│   ├── _helpers.tpl
│   ├── deployment.yaml
│   ├── hpa.yaml
│   ├── ingress.yaml
│   ├── service.yaml
│   ├── serviceaccount.yaml
│   └── tests/
│       └── test-connection.yaml
└── .helmignore
```

This is a representative generated Helm starter structure. The exact files can vary by Helm version and starter configuration.

Every major component has a different responsibility.

| Component          | Responsibility                                      |
| ------------------ | --------------------------------------------------- |
| `Chart.yaml`       | Chart identity, metadata, version, and dependencies |
| `values.yaml`      | Default configuration values                        |
| `templates/`       | Templates used to generate Kubernetes manifests     |
| `charts/`          | Bundled chart dependencies                          |
| `_helpers.tpl`     | Reusable named template definitions                 |
| `NOTES.txt`        | Release-related instructions displayed to users     |
| `templates/tests/` | Helm test resources                                 |
| `.helmignore`      | Files excluded when packaging the chart             |

Do not memorize only the filenames. Understand why the files are separated.

# 5. `Chart.yaml`: The chart identity

`Chart.yaml` contains chart metadata.

It answers:

```
What is this chart?
What is its name?
What does it package?
What version is the chart?
What application version does it represent?
What dependencies does it declare?
```

A simplified example:

```
apiVersion: v2
name: my-chart
description: A Helm chart for a sample web application
type: application
version: 0.1.0
appVersion: "1.0.0"
```

Let's examine each field.

## 5.1 `apiVersion`

```
apiVersion: v2
```

This identifies the Helm chart metadata API version.

For modern Helm chart format, `v2` is the standard format.

Do not confuse this with the Kubernetes resource API version.

Compare:

```
# Helm chart metadata
apiVersion: v2
```

with:

```
# Kubernetes Deployment
apiVersion: apps/v1
```

They describe different things.

One describes a Helm chart.

The other describes a Kubernetes API resource.

## 5.2 `name`

```
name: my-chart
```

The chart name identifies the package.

Chart names should be clear, stable, and meaningful.

Good examples:

```
payments-api
customer-portal
internal-web
monitoring-agent
```

Poor examples:

```
test123
stuff
newchart
final-final
```

Avoid embedding environment names in the chart name when the same chart is intended for reuse across environments.

For example, prefer:

```
payments-api
```

with environment-specific values rather than maintaining unrelated charts named:

```
payments-api-dev
payments-api-staging
payments-api-prod
```

unless there is a genuine architectural reason.

## 5.3 `description`

```
description: A Helm chart for a sample web application
```

The description explains the chart's purpose.

A useful description identifies the application or component the chart packages.

For example:

```
description: Deploys the internal payments API to Kubernetes
```

Descriptions help people understand a chart without opening every template.

## 5.4 `type`

```
type: application
```

Helm supports two major chart types:

```
application
library
```

An application chart represents a deployable application or Kubernetes component.

A library chart provides reusable template functionality for other charts.

We will examine the distinction later.

## 5.5 `version`

```
version: 0.1.0
```

This is the chart version.

It identifies a version of the Helm package.

It is not necessarily the version of the containerized application.

## 5.6 `appVersion`

```
appVersion: "1.0.0"
```

This is informational application version metadata.

Helm does not automatically force your Deployment image to use this version.

For example, a template might reference:

```
image: nginx:1.27
```

while the chart metadata says:

```
appVersion: "1.0.0"
```

That mismatch is technically possible.

Good chart design should make version relationships intentional and understandable.

Quote `appVersion` because application versions may contain strings that YAML could otherwise interpret unexpectedly.

# 6. Chart version vs application version

This distinction is one of the most important concepts in Helm.

CHART VERSION

# 0.3.0

Version of the Helm packaging, templates, and chart configuration.

APPLICATION VERSION

# 2.1.0

Version of the application represented by the chart.

Conceptually:

```
Chart Version
≠
Application Version
```

Consider:

| Change                   | Chart version | Application version |
| ------------------------ | ------------- | ------------------- |
| First release            | 0.1.0         | 1.0.0               |
| Fix Service template     | 0.1.1         | 1.0.0               |
| Add optional Ingress     | 0.2.0         | 1.0.0               |
| Deploy application 1.1.0 | 0.3.0         | 1.1.0               |
| Fix chart helper naming  | 0.3.1         | 1.1.0               |

These are illustrative version choices, not automatic Helm rules.

The chart version changes when you publish a changed chart package.

The application version changes when the application release changes.

## Important production implication

Suppose a team changes:

```
resources:
  requests:
    cpu: 100m
```

to:

```
resources:
  requests:
    cpu: 250m
```

The application binary may be unchanged.

But the chart's default deployment configuration changed.

If publishing the updated chart, the chart version should advance even though the application version can remain the same.

# 7. Semantic versioning concepts

Helm chart versions use Semantic Versioning conventions.

A common version shape is:

```
MAJOR.MINOR.PATCH
```

Example:

```
2.4.7
```

Interpretation:

```
2 = Major
4 = Minor
7 = Patch
```

Typical meanings:

- Major: incompatible changes to the chart's interface or behavior.
- Minor: backward-compatible functionality or features.
- Patch: backward-compatible fixes.

A pre-release version may look like:

```
1.0.0-rc.1
```

A chart may also use build metadata where supported by the relevant packaging and repository tooling.

Production teams should define what counts as a breaking change to their chart interface.

Examples of potentially breaking changes include removing a supported value, changing resource naming conventions, or changing how persistent storage is configured.

# 8. Additional `Chart.yaml` metadata

A production chart can contain more than the basic fields.

For example:

```
apiVersion: v2
name: payments-api
description: Deploys the payments API
type: application
version: 1.2.0
appVersion: "3.4.1"

home: https://example.com/payments

sources:
  - https://example.com/payments/source

keywords:
  - payments
  - api

maintainers:
  - name: Platform Team

annotations:
  example.com/owner: platform-team
  example.com/tier: backend
```

These example URLs and annotations are illustrative.

## Maintainers

The `maintainers` field identifies chart maintainers.

It is useful for ownership and support.

It does not automatically grant permissions or create Kubernetes RBAC identities.

## Annotations

Chart annotations provide additional metadata.

They are different from annotations placed on Kubernetes resources by templates.

For example:

```
annotations:
  example.com/team: platform
```

in `Chart.yaml` does not automatically place that annotation on every Deployment.

If Kubernetes resources need annotations, templates must render them.

# 9. `values.yaml`: Default configuration

`values.yaml` is the default configuration interface for a chart.

It answers:

```
Which parts of the chart can users configure?
```

For example:

```
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi
```

These values do not directly create Kubernetes resources.

They become useful when templates reference them.

Example:

```
replicas: {{ .Values.replicaCount }}
```

Helm substitutes the supplied value during rendering.

With:

```
replicaCount: 2
```

the rendered manifest contains:

```
replicas: 2
```

The relationship is:

```
values.yaml
    │
    ▼
.Values
    │
    ▼
Template expression
    │
    ▼
Rendered Kubernetes YAML
```

## Values are not magic

Adding:

```
enableMonitoring: true
```

to `values.yaml` does not automatically deploy monitoring.

A template must use the value to control what gets rendered.

This is a common beginner misunderstanding.

# 10. Values as the chart interface

Think of a chart as a reusable component.

Its values are configurable inputs.

For example:

```
Chart
│
├── Input: replicaCount
├── Input: image.repository
├── Input: image.tag
├── Input: service.port
└── Input: resources
```

Those inputs influence generated Kubernetes configuration.

Good chart design exposes meaningful configuration without forcing users to understand every internal template.

Bad chart design exposes hundreds of unrelated values without clear documentation or consistency.

## Environment differences

The same chart may be used with different values.

Development:

```
replicaCount: 1
```

Production:

```
replicaCount: 3
```

This is one of Helm's primary benefits.

You do not need to duplicate the entire Deployment template just to change the replica count.

# 11. `templates/`: The rendering engine's input

The `templates/` directory contains Helm templates.

Most of these templates generate Kubernetes resource definitions.

Example:

```
templates/
├── deployment.yaml
├── service.yaml
├── configmap.yaml
└── ingress.yaml
```

Helm uses Go's template language with additional Helm functions.

Templates can include:

```
Variables
Expressions
Conditionals
Loops
Functions
Named templates
```

For example:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
```

If the release name is:

```
web
```

the rendered resource contains:

```
metadata:
  name: web
```

Helm templates are source files.

Rendered manifests are the resulting Kubernetes YAML.

# 12. Template source vs rendered output

Template source

deployment.yaml

```
replicas: {{ .Values.replicaCount }}
```

Contains Helm expressions.

Rendered output

Kubernetes manifest

```
replicas: 3
```

Contains concrete values.

Kubernetes does not evaluate Helm template expressions.

Helm renders the templates first.

This is why a Helm template containing:

```
{{ .Values.replicaCount }}
```

cannot simply be sent unchanged to the Kubernetes API as a valid replica count.

# 13. Common Helm template objects

Helm makes several built-in objects available during template rendering.

Important examples:

| Object          | Purpose                                            |
| --------------- | -------------------------------------------------- |
| `.Values`       | Chart configuration values                         |
| `.Chart`        | Chart metadata                                     |
| `.Release`      | Release information                                |
| `.Capabilities` | Kubernetes API capabilities available to rendering |
| `.Template`     | Information about the current template             |
| `.Files`        | Access to eligible files packaged with the chart   |

Examples:

```
{{ .Values.replicaCount }}
```

```
{{ .Chart.Name }}
```

```
{{ .Chart.Version }}
```

```
{{ .Release.Name }}
```

```
{{ .Release.Namespace }}
```

These expressions are evaluated by Helm, not Kubernetes.

Later chapters will explore template functions, scoping, pipelines, and reusable helpers in depth.

For now, the important goal is recognizing where rendered values originate.

# 14. `deployment.yaml`: Workload definition

A Deployment template usually describes a Kubernetes Deployment.

A simplified example:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: 80
```

With appropriate values, this produces a Deployment manifest.

The relationship is:

```
deployment.yaml
+
values.yaml
+
Release information
↓
Helm rendering
↓
Kubernetes Deployment
↓
ReplicaSet
↓
Pods
```

The Deployment controller, not Helm itself, manages the ongoing replica reconciliation.

# 15. `service.yaml`: Stable application access

A Service template describes Kubernetes service discovery and connectivity.

Example:

```
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}
spec:
  type: {{ .Values.service.type }}
  selector:
    app: {{ .Release.Name }}
  ports:
    - port: {{ .Values.service.port }}
      targetPort: 80
```

The Service selector must match the labels on the intended Pods.

If the selector does not match, the Service may exist but have no usable endpoints.

This is an important distinction:

```
Helm render succeeded
↓
Kubernetes accepted Service
↓
Service selector incorrect
↓
No matching Pods
↓
Application traffic fails
```

Successful chart rendering is not proof of correct application behavior.

# 16. `ingress.yaml`: Optional external routing

An Ingress template can describe HTTP or HTTPS routing rules.

Many starter charts use a value such as:

```
ingress:
  enabled: false
```

The template may contain:

```
{{- if .Values.ingress.enabled }}
```

When the value is false, the Ingress resource is not rendered.

When true, the template may render an Ingress.

This demonstrates an important concept:

Not every template necessarily produces a resource on every rendering.

Also, creating an Ingress resource does not itself install an Ingress controller.

That infrastructure must exist separately.

# 17. `hpa.yaml`: Autoscaling configuration

The HorizontalPodAutoscaler template describes Kubernetes horizontal workload scaling.

A chart might expose:

```
autoscaling:
  enabled: false
  minReplicas: 1
  maxReplicas: 5
  targetCPUUtilizationPercentage: 70
```

If enabled, an HPA template can render a HorizontalPodAutoscaler resource.

An HPA needs appropriate metrics and workload configuration to function.

The important anatomy lesson is that the chart can make autoscaling optional.

```
Values
↓
autoscaling.enabled
↓
Template condition
├── true  → Render HPA
└── false → Omit HPA
```

# 18. `serviceaccount.yaml`: Workload identity

A ServiceAccount template can create a Kubernetes ServiceAccount.

For example:

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: {{ .Release.Name }}
```

A ServiceAccount provides a Kubernetes workload identity.

It does not automatically grant broad Kubernetes API permissions.

Those permissions require appropriate authorization configuration, typically RBAC.

Production charts should avoid creating unnecessary identities or permissions.

# 19. `_helpers.tpl`: Reusable named templates

The `_helpers.tpl` file commonly contains named template definitions.

For example:

```
{{- define "my-chart.name" -}}
{{- .Chart.Name -}}
{{- end -}}
```

Another template can reference it:

```
{{ include "my-chart.name" . }}
```

This allows reuse.

Without helpers, you might repeat naming logic in:

```
deployment.yaml
service.yaml
serviceaccount.yaml
ingress.yaml
```

With helpers:

```
_helpers.tpl
↓
Reusable naming logic
↓
Multiple templates
```

## Why helpers matter

Production charts often need consistent:

```
Resource names
Labels
Selectors
Annotations
ServiceAccount names
```

Helpers reduce duplication and inconsistent implementations.

They are particularly useful for generating standardized Kubernetes labels.

## Important distinction

Files beginning with `_` inside the templates directory are treated as helper/partial files rather than directly rendered Kubernetes manifests.

Named templates defined inside them can be called by other templates.

# 20. Naming helpers and resource naming

Consider a chart named:

```
payments-api
```

installed as a release named:

```
payments
```

A helper might generate:

```
payments-payments-api
```

as a resource name.

Different charts use different naming conventions.

Do not assume every resource name equals the release name.

This matters during troubleshooting.

A release may be named:

```
payments
```

while the Deployment is named:

```
payments-payments-api
```

The chart's helpers often explain why.

Run:

```
cat my-chart/templates/_helpers.tpl
```

Look for:

```
{{ define
```

and:


# 21. `NOTES.txt`: Release information

`templates/NOTES.txt` is used to generate information displayed after certain Helm operations.

A chart may use it to explain:

```
How to access the application
How to port-forward
How to inspect the release
How to obtain the service endpoint
```

Example:

```
Application release: {{ .Release.Name }}

Namespace: {{ .Release.Namespace }}

Check the workload:

kubectl get pods -n {{ .Release.Namespace }}
```

After installation, Helm can display the rendered notes.

Notes can also be inspected with commands such as:

```
helm get notes RELEASE_NAME -n helm-lab
```

## Important distinction

`NOTES.txt` is not a Kubernetes resource.

It does not create a Pod, Deployment, or Service.

It is informational output.

## Security consideration

Do not place secrets or sensitive tokens in release notes.

Release information may be displayed in terminals, CI logs, or retrieved later.

# 22. `charts/`: Chart dependencies

The `charts/` directory is used for chart dependencies.

Imagine an application chart that relies on other packaged components.

Conceptually:

```
application-chart/
│
├── Chart.yaml
├── values.yaml
├── templates/
└── charts/
    ├── dependency-a/
    └── dependency-b/
```

A chart dependency may be declared in `Chart.yaml`.

Example:

```
dependencies:
  - name: redis
    version: "20.0.0"
    repository: "https://charts.example.com"
    condition: redis.enabled
```

This is an illustrative dependency declaration, not a verified repository/version combination.

The dependency fields include:

```
name
version
repository
condition
```

The `condition` can control whether the dependency is enabled through values.

## Dependency management commands

Common commands include:

```
helm dependency list ./my-chart
```

```
helm dependency update ./my-chart
```

```
helm dependency build ./my-chart
```

`helm dependency update` resolves declared dependencies and updates dependency lock information.

`helm dependency build` is used to reconstruct dependencies based on lock information when available.

## `Chart.lock`

A chart with resolved dependencies may contain:

```
Chart.lock
```

This records resolved dependency information.

For reproducible builds, dependency declarations and lock information matter.

## Production caution

Dependencies can introduce:

```
Additional Kubernetes resources
Additional security permissions
Additional services
Operational dependencies
Supply-chain risks
```

Do not add a dependency simply because it is convenient.

Understand what it installs and how it is maintained.

# 23. `templates/tests/`: Helm tests

Helm supports test resources that can be run against an installed release.

A starter chart may include:

```
templates/tests/test-connection.yaml
```

A test commonly creates a Kubernetes Job or Pod annotated as a Helm test hook.

Example:

```
apiVersion: v1
kind: Pod
metadata:
  name: "{{ .Release.Name }}-test"
  annotations:
    "helm.sh/hook": test
spec:
  restartPolicy: Never
  containers:
    - name: test
      image: busybox:1.36
      command:
        - /bin/sh
        - -c
        - echo "Helm test executed"
```

This is a simple execution test, not a full application health test.

Run tests with:

```
helm test RELEASE_NAME -n helm-lab
```

Tests can verify things such as:

```
Service connectivity
Application endpoints
Basic credentials
Application initialization
```

## Important distinction

A successful Helm test means the defined test passed.

It does not automatically prove every aspect of the application is healthy.

The quality of the test determines what confidence it provides.

# 24. `.helmignore`: Packaging exclusions

The `.helmignore` file tells Helm which files should be excluded when packaging a chart.

Example:

```
.git/
*.swp
*.tmp
.DS_Store
```

This helps prevent unnecessary development files from entering packaged chart archives.

For example:

```
my-chart/
├── Chart.yaml
├── values.yaml
├── templates/
├── debug-output.tmp
└── .helmignore
```

If the ignore rules exclude `*.tmp`, the temporary file should not be included in the packaged chart.

## Security caution

`.helmignore` is not a secrets-management system.

Do not rely on it as the primary protection against accidentally committing or distributing secrets.

Secrets should be managed through appropriate secret-management workflows.

Also remember that `.gitignore` and `.helmignore` serve different purposes.

| File          | Primary purpose                                   |
| ------------- | ------------------------------------------------- |
| `.gitignore`  | Controls which untracked files Git ignores        |
| `.helmignore` | Controls files excluded from Helm chart packaging |

# 25. Other important chart files

As charts become more mature, you may encounter additional files.

## `values.schema.json`

A JSON Schema file can validate chart values.

Example use cases:

```
Require a service port
Validate value types
Restrict allowed strings
Reject invalid configurations
```

This is valuable because a value can be syntactically valid YAML but logically invalid for the chart.

For example:

```
replicaCount: "many"
```

is valid YAML, but not a valid integer replica count for a Deployment.

A values schema can detect this earlier.

## `README.md`

A chart README commonly documents:

```
Purpose
Prerequisites
Installation
Configuration values
Examples
Upgrades
Troubleshooting
Ownership
```

A chart should not require users to reverse-engineer every template to discover supported configuration.

## `crds/`

Some charts include a `crds/` directory for CustomResourceDefinition files.

CRDs have special lifecycle behavior in Helm.

For example, Helm does not manage CRD upgrades and deletions like ordinary templated resources.

Do not assume CRDs behave exactly like Deployments or Services.

This becomes important when packaging operators and platform components.

# 26. Application charts vs library charts

Helm has two major chart types.

Application chart

Deployable

Contains templates for resources such as Deployments, Services, and ConfigMaps.

Library chart

Reusable logic

Provides helper templates and shared functionality for other charts.

An application chart:

```
type: application
```

A library chart:

```
type: library
```

## Application chart example

```
payments-api/
├── Chart.yaml
```

It can render deployable Kubernetes resource manifests.

## Library chart example

```
platform-library/
├── Chart.yaml
└── templates/
    └── _helpers.tpl
```

A library chart is intended to supply reusable template logic to other charts.

It is not independently installed as a normal deployable application chart.

## When library charts help

Suppose an organization maintains:

```
payments
orders
inventory
customers
```

Each application needs consistent:

```
Labels
Naming
Security context
Annotations
Deployment conventions
```

A library chart can centralize reusable template patterns.

However, library charts can also create coupling.

Changing a shared helper may affect many consuming charts.

Use library charts where reuse is meaningful, not merely to avoid a few lines of YAML.

# 27. Chart naming standards

Chart naming should be consistent and predictable.

Recommended principles:

- Use lowercase names.
- Prefer hyphens between words.
- Use meaningful application or component names.
- Avoid unnecessary environment suffixes.
- Keep chart identity stable.
- Avoid embedding chart versions into the chart name.

Examples:

```
payments-api
customer-portal
internal-gateway
monitoring-agent
```

Avoid:

```
Payments_API
mychartFINAL
prod-chart-v3
```

Chart names, release names, and Kubernetes resource names are related but distinct concepts.

A chart named `payments-api` can be installed with a release name of `payments`.

That distinction is fundamental to understanding Helm-generated resource names.

# 31. Removing unnecessary generated resources

The `helm create` command provides a starter chart.

A real application may not need every generated component.

For example, a simple internal web service may not need:

```
Ingress
HorizontalPodAutoscaler
ServiceAccount creation
```

at the beginning.

You can remove unused templates.

But first inspect the references between them.

For example, deleting a ServiceAccount template while the Deployment still references its generated name may cause the workload to reference a nonexistent ServiceAccount.

Likewise, removing a Service while leaving an Ingress that references it can break routing.

## Safe removal workflow

```
Identify unused resource
↓
Inspect corresponding template
↓
Find references from other templates
↓
Find associated values
↓
Remove or adjust references
↓
Remove unused template
↓
Render
↓
Lint
↓
Inspect output
```

Avoid blindly deleting files based only on their names.

# 37. Create `deployment.yaml`

Create:

```
minimal-web/templates/deployment.yaml
```

Contents:

```
apiVersion: apps/v1
kind: Deployment

metadata:
  name: {{ .Release.Name }}-web
  labels:
    app.kubernetes.io/name: minimal-web
    app.kubernetes.io/instance: {{ .Release.Name }}

spec:
  replicas: {{ .Values.replicaCount }}

  selector:
    matchLabels:
      app.kubernetes.io/instance: {{ .Release.Name }}

  template:
    metadata:
      labels:
        app.kubernetes.io/name: minimal-web
        app.kubernetes.io/instance: {{ .Release.Name }}

    spec:
      containers:
        - name: nginx
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}

          ports:
            - name: http
              containerPort: 80
```

Understand each dynamic expression.

| Expression                 | Source                   |
| -------------------------- | ------------------------ |
| `.Release.Name`            | Helm release information |
| `.Values.replicaCount`     | `values.yaml`            |
| `.Values.image.repository` | `values.yaml`            |
| `.Values.image.tag`        | `values.yaml`            |
| `.Values.image.pullPolicy` | `values.yaml`            |

The Pod labels must match the Deployment selector.

# 38. Create `service.yaml`


Contents:

```
metadata:

  labels:
    app.kubernetes.io/name: minimal-web
    app.kubernetes.io/instance: {{ .Release.Name }}

  type: {{ .Values.service.type }}
```

# 54. Chart anatomy troubleshooting model

When a chart fails, investigate in order:

Chart.yaml

values.yaml

templates/

Template expressions

Rendered YAML

Kubernetes validation

Kubernetes resources

Application behavior

This helps separate chart-level errors from Kubernetes-level and application-level errors.

For example:

```
Invalid Chart.yaml
→ Chart metadata problem

Undefined value
→ Template/value interface problem

Invalid rendered resource
→ Kubernetes schema problem

Service without endpoints
→ Selector/workload relationship problem

Pod CrashLoopBackOff
→ Container/application runtime problem
```

Do not assume every failed Helm deployment is caused by Helm itself.

# 56. Production chart design standards

A maintainable chart should follow several principles.

Clear ownership: The chart should have documented maintainers and a clear purpose.

Stable configuration interface: Values should be named consistently and changes should be reviewed for backward compatibility.

Predictable resource naming: Names should avoid unnecessary collisions and unexpected changes during upgrades.

Consistent labels: Labels and selectors should follow established conventions and remain compatible.

Minimal permissions: Do not create unnecessary ServiceAccounts, Roles, or ClusterRoles.

Dependency control: Declare, review, and pin dependencies appropriately.

Validation: Run Helm linting, rendering, Kubernetes schema validation, and functional tests.

Documentation: Explain required values, optional features, and deployment prerequisites.

Version discipline: Advance chart versions when publishing changed chart packages.

Security: Never embed production secrets directly in a chart package.

# 57. The chart as an engineering interface

A production chart is not merely a collection of YAML files.

It has an interface.

Chart inputs

Values · release name · namespace · capabilities

Chart implementation

Templates · helpers · dependencies

Chart outputs

Kubernetes manifests · release notes · test resources

A well-designed chart allows users to configure intended behavior without modifying internal templates for every environment.

That is what makes Helm packaging reusable.
