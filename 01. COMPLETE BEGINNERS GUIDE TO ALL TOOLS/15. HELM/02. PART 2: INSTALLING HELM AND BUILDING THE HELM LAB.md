# PART 2: INSTALLING HELM AND BUILDING THE HELM LAB

## Goal

Build a **safe, repeatable Helm learning environment**, understand how the Helm CLI is structured, understand exactly how Helm finds and authenticates to Kubernetes, and learn how to prevent one of the most dangerous operational mistakes in Kubernetes:

```text
Running the correct command
against the wrong cluster.
```

By the end of this part, you should be able to:

```text
Install Helm
↓
Verify Helm
↓
Verify kubectl
↓
Understand kubeconfig
↓
Understand contexts
↓
Create a disposable Kubernetes cluster
↓
Verify cluster connectivity
↓
Create a dedicated Helm namespace
↓
Use Helm with explicit cluster and namespace targeting
↓
Switch contexts safely
↓
Recognize wrong-context mistakes
↓
Recognize wrong-namespace mistakes
↓
Diagnose authentication failures
↓
Diagnose authorization failures
↓
Diagnose invalid kubeconfig
↓
Clean up the lab safely
```

The central operational model for this chapter is:

```text
Engineer
↓
Helm CLI
↓
kubeconfig
↓
context
↓
cluster + identity + namespace
↓
Kubernetes API
↓

↓

↓

```

# 1. WHY BUILD A HELM LAB?

You could install Helm and immediately point it at an existing Kubernetes cluster.

That would be a bad way to learn.

Helm can create, modify, and delete real Kubernetes resources.

A command such as:

```bash
helm install
```

can potentially create:

```text
Deployments
Services
ConfigMaps
Secrets
ServiceAccounts
Roles
RoleBindings
ClusterRoles
ClusterRoleBindings
Ingresses
Jobs
PersistentVolumeClaims
Custom Resources
```

depending on the chart.

A command such as:

```bash
helm uninstall
```

can remove resources belonging to a release.

Therefore, experimentation should happen in an environment where mistakes are inexpensive.

# 4. WHY KIND FOR THE PRIMARY LAB?

kind means:

```text
Kubernetes IN Docker
```

It creates Kubernetes nodes using containers.

For learning Helm, kind provides several advantages:

```text

Fast to destroy
Easy to automate
Works well with CI
Supports multiple clusters
Uses normal kubeconfig/context concepts
Uses normal kubectl
Uses normal Helm
```

This is valuable because Helm behaves against kind much like it behaves against another Kubernetes API.

# 12. PREREQUISITE 2: KUBECTL

`kubectl` is the standard Kubernetes command-line client.

You will use it constantly alongside Helm.

Helm answers questions such as:

```text
What releases exist?

What chart was installed?

What values were used?

What revision exists?
```

kubectl answers questions such as:

```text
Which Pods exist?

Is the Deployment ready?

What events occurred?

What does this resource look like?

Why is this Pod failing?
```

# 15. PREREQUISITE 3: KUBECONFIG

Kubernetes clients need information describing how to reach Kubernetes clusters.

This configuration is commonly called:

```text
kubeconfig
```

A kubeconfig can contain information about:

```text
Clusters
Users / credentials
Contexts
Current context
```

---

# 16. DEFAULT KUBECONFIG LOCATION

A common default location on Linux and macOS is:

```text
$HOME/.kube/config
```

Conceptually:

```text
~/.kube/config
```

But do not assume this is always the only configuration source.

Kubernetes clients can also use:

```text
KUBECONFIG environment variable
```

or an explicitly supplied kubeconfig path.

---

# 17. KUBECONFIG IS NOT THE CLUSTER

Important distinction:

```text
Kubeconfig
≠
Kubernetes cluster
```

The kubeconfig is client configuration describing how to connect.

Think:

```text
kubeconfig
=
connection and identity configuration
```

not:

```text
kubeconfig
=
Kubernetes itself
```

---

# 18. BASIC KUBECONFIG STRUCTURE

A simplified kubeconfig may conceptually contain:

```yaml
apiVersion: v1
kind: Config

clusters:
  - name: helm-lab-cluster
    cluster:
      server: https://example

users:
  - name: helm-lab-user
    user:
      # authentication configuration

contexts:
  - name: helm-lab
    context:
      cluster: helm-lab-cluster
      user: helm-lab-user
      namespace: helm-lab

current-context: helm-lab
```

Do not copy this as a working kubeconfig.

It exists to teach the structure.

---

# 19. THE THREE IMPORTANT KUBECONFIG OBJECTS

Think:

```text
Cluster
=
Where?

User
=
Who?

Context
=
Which cluster + which identity + optional namespace?
```

This is one of the most important Kubernetes CLI mental models.

# 23. CURRENT CONTEXT

Your kubeconfig can designate a current context.

Check it with:

```bash
kubectl config current-context
```

Example:

```text
kind-helm-lab
```

That single command should become muscle memory.

---

# 24. WHY CURRENT CONTEXT MATTERS

Imagine your kubeconfig contains:

```text
kind-helm-lab

development

staging

production
```

If the current context is:

```text
production
```

then an unqualified command may target production.

For example:

```bash
helm uninstall payments
```

is a very different operation depending on context.

The command may be syntactically perfect.

The target may be catastrophically wrong.

---

# 25. THE DANGEROUS MENTAL MODEL

Never think:

```text
I know what command I typed,
therefore I know what will happen.
```

Think:

```text
Command
+
Cluster
+
Namespace
+
Identity
=
Actual Operation
```

# 26. PREREQUISITE 4: NAMESPACE

A Kubernetes namespace provides a scope for many namespaced resources.

Examples:

```text
default
kube-system
development
staging
production
helm-lab
```

A namespace helps organize and isolate resource names and policy boundaries.

It is not a complete security boundary by itself.

---

# 27. NAMESPACE MATTERS TO HELM

Helm releases are namespace-scoped.

Therefore:

```text
Release name
+
Namespace
```

matters when locating a release.

For example, a release named:

```text
web
```

in:

```text
development
```

is not the same release identity as:

```text
web
```

in:

```text
production
```

---

# 28. WRONG NAMESPACE CAN LOOK LIKE A MISSING RELEASE

Suppose:

```text
payments
```

is installed in:

```text
helm-lab
```

You run:

```bash
helm list -n default
```

and see nothing.

That does not prove:

```text
payments does not exist.
```

It proves:

```text
payments was not shown in that namespace query.
```

This distinction matters enormously during troubleshooting.


# 210. KNOWLEDGE CHECK 13

# 213. KNOWLEDGE CHECK 16

Does a namespace provide complete security isolation?

Answer:

No.

Namespaces provide important organizational and policy scope, but strong isolation requires additional controls such as RBAC, network policies, workload security controls, resource governance, and potentially separate clusters/accounts depending on the threat model.

Prefer appropriately scoped, short-lived access mechanisms where supported.
